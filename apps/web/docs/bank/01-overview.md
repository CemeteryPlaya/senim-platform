# 01. Обзор продукта

Документ для банка-партнёра: что делает «Сенім», кто его пользователи, как устроены путь сделки и деньги. Описание соответствует ТЗ MVP v1.0 и решению [ADR-009](../adr/009-tz-v1-money-model.md). Ссылки на файлы даны для проверки по коду (ветка `feat/tz-v1`). Название продукта рабочее и хранится в одном месте — `src/config/brand.ts`: товарный знак на проверке.

## Что это

«Сенім» — платформа безопасных сделок на мебель на заказ: PWA для телефона, интерфейс на русском. Покупатель создаёт заказ, мастера (ИП, ТОО, самозанятые) откликаются, стороны договариваются о цене в чате. Акцепт цены порождает оферту; покупатель оплачивает, мастер выполняет и сдаёт работу с фото, покупатель подписывает акт, мастер получает выплату.

Платформа продаёт одно — спокойствие за деньги. Поэтому первый блок карточки заказа — **статус денег**, а не статус работ. Блок строится из журнала операций с деньгами (ТЗ п. 4).

## Деньги

**Железное правило: деньги клиентов никогда не проходят через счета ТОО.** Деньги покупателя лежат на эскроу-счёте сделки в банке. Платформа фиксирует операции и передаёт банку распоряжения или пакет документов. Деньги она не держит. На счёт ТОО банк перечисляет только доход платформы, и только после подписанного акта.

| | Формула (ТЗ п. 6) | X = 1 500 000 ₸ |
|---|---|---|
| Покупатель вносит на эскроу-счёт | X + защита сделки 2% | 1 530 000 ₸ |
| Мастер получает после акта | X − гарантия оплаты и клиента 4% | 1 440 000 ₸ |
| Доход платформы | оплачено − выплата | 90 000 ₸ |

- Одна оплата покупателя в начале (`HOLD`) и одна выплата мастеру в конце (`RELEASE` → `SPLIT_MASTER` + `SPLIT_PLATFORM`). Авансов нет.
- Возврат покупателю (`REFUND`) — при отмене после оплаты и по решению спора. Пока спор открыт, выплата заморожена (`FREEZE` / `UNFREEZE`).
- Суммы — в тиынах, целыми числами. Защита округляется вверх до тиына, выплата — вниз; «оплачено = выплата + доход платформы» верно до тиына и проверяется автотестами (`src/modules/payments/money.ts`).
- Журнал денег (`MoneyTransaction`) — единственный источник правды. Каждая операция несёт ключ идемпотентности; повтор не создаёт дубль. Журнал только на добавление (триггер базы).
- Термины интерфейса: покупатель видит «Защита сделки (2%)», мастер — «Гарантия оплаты и клиента (4%)»; других названий для этих сумм в интерфейсе нет (инвариант проекта; тест текстов добавляется при переводе экранов). В экранах покупателя и мастера нет слова «эскроу»: вместо него — «деньги в банке под защитой». Слово «эскроу» есть в оферте, договорах, документах для банка и у оператора.

### Платёжные провайдеры

Банк не вшит в бизнес-логику: ядро сделки работает с интерфейсом `PaymentProvider` (`src/modules/payments/provider.ts`). Провайдер выбирается переменной `PAYMENT_PROVIDER` и фиксируется в сделке при её создании.

| Провайдер | Где | Что это |
|---|---|---|
| `mock` | разработка, демо | Тестовые платежи, подтверждаются сразу; в интерфейсе помечены «тестовый платёж». Запрещён в `prod` |
| `manual` | пилот (`prod`) | **Мост к эскроу Freedom Bank.** У банка эскроу без API: трёхсторонний договор, открытие и обслуживание 0 ₸, раскрытие по расписке. Оператор проставляет статусы денег кнопками «Деньги поступили на счёт в банке», «Выплачено мастеру», «Доход платформы получен», «Возврат покупателю» — каждое с номером, датой и сканом банковского документа. Пилот идёт на этом провайдере с реальными деньгами в банке |
| `freedompay` | только `staging` | Песочница Freedom Pay ([07-freedompay-integration.md](07-freedompay-integration.md)). С реальными деньгами не используется, пока не подтверждена схема без зачисления на баланс ТОО ([06](06-bank-api-landscape.md)) |
| `bcc` | — | Банк ЦентрКредит: только интерфейс и TODO до получения документации Escrow API |

Подробно — [03-escrow-integration.md](03-escrow-integration.md); обзор банков — [06-bank-api-landscape.md](06-bank-api-landscape.md).

## Роли

| Роль (ТЗ) | В коде | Что делает |
|---|---|---|
| Покупатель (физлицо) | `Role.CLIENT` | Создаёт заказ, выбирает мастера, торгуется в чате, подписывает оферту, оплачивает, принимает работу и подписывает акт, открывает спор, отменяет до начала работ |
| Мастер (ИП, ТОО, самозанятый) | `Role.EXECUTOR`, `ExecutorProfile` | Проходит проверку оператором (KYC: удостоверение и регистрация ИП/ТОО), указывает реквизиты выплаты (KZ IBAN), откликается, торгуется, подписывает оферту, выполняет, сдаёт с фото, получает выплату |
| Админ (оператор платформы) | `Role.OPERATOR` | Модерация мастеров и KYC, ручное управление статусами денег в `manual`, формирование пакета на раскрытие, разбор споров, журнал аудита |

- Контакты сторон (телефон, Instagram) скрыты до заключения оферты: «заключена» значит подписана обеими сторонами (`Deal.signedAt`). До этого в чате маскируются телефоны, e-mail и ссылки на мессенджеры. После оферты контакты видны обеим сторонам сделки.
- Имя мастера покупатель видит по режиму показа, который выбирает оператор: по умолчанию «Исполнитель №N» ([ADR-006](../adr/006-executor-identity-visibility.md)). ИИН/БИН раскрываются только в договоре; в интерфейсе — последние 4 цифры.

## Путь сделки

```
заказ → отклики и торг → оферта → оплата → работа → сдача с фото → акт приёмки → выплата
```

1. **Заказ.** На первом шаге — только стиль и тип комнаты. Технические параметры (материалы, фурнитура, размеры) — в свёрнутом блоке «Для продвинутых». У адреса — координаты для проверки сдачи.
2. **Отклики и торг.** Мастера откликаются ценой и сроком. Торг — раунды встречных цен в чате отклика (`PriceProposal`: кто, сумма, когда, статус). Акцепт фиксирует цену X и создаёт сделку в `CREATED` с офертой.
3. **Оферта.** PDF с суммами и сроками. Подписывают обе стороны: собственноручно (рисунок подписи или напечатанное имя, с хэшем документа, временем, IP и устройством) и ЭЦП.
4. **Оплата → `PAID_HOLD`.** Покупатель вносит X + 2% на эскроу-счёт сделки. Статус меняется, когда подтверждена операция `HOLD`: банком или оператором по банковскому документу.
5. **Работа → `IN_PROGRESS`.** Мастер начинает работу. Он может публиковать необязательные фото-отчёты «Ход работ» — без денег и актов.
6. **Сдача → `READY`.** Фото результата обязательно. GPS — мягкая проверка: дальше 500 м от адреса заказа — предупреждение, а не блокировка. Расстояние попадает в акт.
7. **Акт → `ACCEPTED`.** Покупатель подписывает акт приёмки (собственноручно и ЭЦП), мастер — ЭЦП. Акт отправляется обеим сторонам.
8. **Выплата → `SPLIT_PAYOUT`.** Банк выплачивает мастеру X − 4% и перечисляет доход платформы. Статус меняется, когда подтверждены обе операции.

**Отмена.** До оплаты (`CREATED`) отменить может любая сторона. После оплаты, до начала работ (`PAID_HOLD`), покупатель отменяет с полным возвратом — «Деньги вернутся на вашу карту» (`REFUNDED`). После начала работ — только через спор.

**Спор.** Открывает любая сторона в `PAID_HOLD`, `IN_PROGRESS` или `READY`. Открытый спор блокирует выплату и все переходы, кроме решения. Решает оператор: продолжить работу, полный возврат или частичный раздел (мастеру часть Y из X по той же формуле, остаток — покупателю).

Переходы строго последовательные, перескоки запрещены кодом (таблица переходов, [02-architecture.md](02-architecture.md)). Каждое изменение сделки и каждое действие с деньгами пишется в журнал аудита: кто, что, когда, откуда.

## Документы сделки

| Документ | Когда | Кто подписывает |
|---|---|---|
| Оферта (`CONTRACT`) | акцепт цены | обе стороны: собственноручно и ЭЦП |
| Акт приёмки (`ACCEPTANCE_ACT`) с фото сдачи и GPS-отметкой | сдача | покупатель — собственноручно и ЭЦП; мастер — ЭЦП |
| Выписка по деньгам (`MONEY_STATEMENT`) | в любой момент | — (проекция журнала денег) |
| Расписка на раскрытие (`RELEASE_RECEIPT`) | после акта, для банка в `manual` | по порядку банка; **шаблон требует юридической проверки** |

Документы открываются с телефона, скачиваются и пересылаются.

## Объём Фазы 1 и флаги

Возможности вне Фазы 1 ТЗ не удалены, а выключены флагами (`src/platform/features.ts`, переменные `FEATURE_*` и `AI_ENABLED`). Оператор видит состояние флагов только для чтения.

| Флаг | Что включает | По умолчанию |
|---|---|---|
| `ai` | помощник по заявке, иллюстрация помещения, подсказки в споре | выключен |
| `preContractFlows` | сценарии до договора 2–5, замерщик площадки, залог за выезд | выключен |
| `materialsCalculator` | калькулятор материалов | выключен |
| `reviews`, `dealPortfolio`, `inspiration` | отзывы, портфолио из сделки, лента «Вдохновение» (Фаза 2) | выключены |
| `publicShowcase` | публичная витрина сделки (страница — Фаза 2; фундамент — `Deal.publicId` и согласия сторон) | выключен |
| `executorHandSignsAct` | собственноручная подпись мастера на акте | выключен |
| `clientPhoneConsent` | показ телефона покупателя до оферты по согласию (противоречит ТЗ п. 3) | выключен |

## Внешние сервисы

Все внешние сервисы стоят за интерфейсами с моком. Выбор реализации — переменной окружения, проверенной в `src/platform/env.ts`. API сервисов без документации не выдумываются: есть интерфейс и TODO. Контуры (`APP_ENV`): `dev` — моки; `staging` — песочница Freedom Pay; `prod` — пилот на `manual`, где моки SMS, подписи и платежей, `freedompay` и демо-режим запрещены проверкой окружения.

| Сервис | Переменная | Сейчас | Реальная реализация |
|---|---|---|---|
| Платежи | `PAYMENT_PROVIDER` | `mock` | `manual` (Freedom Bank), `freedompay` (staging), `bcc` (TODO) |
| SMS для входа | `SMS_PROVIDER` | `mock` | `http` — каркас под SMS-шлюз РК |
| Подпись ЭЦП | `SIGNATURE_PROVIDER` | `mock` (в интерфейсе предупреждение) | `sigex` — порт и проверка готовы, HTTP-клиент — по документации SIGEX |
| E-mail (отправка акта) | `EMAIL_PROVIDER` | `mock` | выбирает владелец |
| Геокодер адреса | `GEOCODER_PROVIDER` | `mock` | выбирает владелец; без него покупатель указывает «моё местоположение» |
| Web push | `VAPID_*` | выключен без ключей; уведомления в приложении работают | ключи владельца |
| Хранилище файлов | `STORAGE_PROVIDER` | `local` | `s3` (в том числе облако РК), `vercel-blob` |
