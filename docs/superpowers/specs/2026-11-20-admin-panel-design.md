# Админка администратора — дизайн

Дата: 20.11.2026. Статус: решения владельца собраны в разговоре 19–20.11.2026; после первого показа владелец скажет, какие таблицы и поля закрыть или изменить.

## Интент

Владельцу (Санжар, CTO) нужен один экран, где видно всё, что происходит на платформе, и где можно поправить данные, не открывая базу. Слова владельца: «аналог админки в Django и sqladmin», «Админка нужна Администратору, Операторы это другие пользователи, мне надо видеть статистику и управлять работой сайта».

Оператор работает с очередями (KYC, споры, сделки) по правилам процессов. Администратор смотрит на платформу целиком и правит данные там, где процессы этого не делают. Админка не заменяет экраны оператора и не обходит статусные машины.

## Решения владельца (его слова)

1. Отдельная роль «Администратор». «Операторы это другие пользователи» — оператор в админку не попадает.
2. «Из админки нельзя будет менять статус.»
3. «Журнал денег — только чтение.»
4. «ИИН и IBAN будут шифроваться и нельзя будет увидеть их в этой админке» — зашифрованные ПДн не показываются вовсе, даже последние 4 символа.
5. «Изменение в админке идет в аудит и после уже проходит дальше» — запись аудита (старое и новое значение) и само изменение — одна транзакция; без записи аудита изменения нет.
6. «Как увижу сам, напишу какие трогать не буду… или скажу как изменить» — правила доступа к таблицам и полям должны легко меняться после показа.
7. Вход администратора — с обязательной 2FA (как у оператора; подтверждено при обсуждении).

## Цели

1. **Роль ADMIN** в identity и в web. Сотрудник: только эта роль, короткая сессия (как у оператора), второй фактор TOTP обязателен для каждой сессии.
2. **Выдача роли — только из терминала**: `identity grant-admin --phone <E.164>` (как `mfa-reset`). На стенде — сид (`SeedUsers`) с известным TOTP-секретом. Ни переменной окружения, ни флага, ни экрана, которые делают человека администратором.
3. **Статистика** (`/v2/admin`): за период (7 дней, 30 дней, всё время)
   - заявки по статусам; сделки по статусам;
   - деньги — только из журнала денег (`MoneyTransaction`): оплачено покупателями, выплачено мастерам, возвраты, доход платформы = оплачено − выплата по завершённым сделкам; суммы — тиыны (`BigInt`), вывод через `Money`/`formatMoney`;
   - мастера по статусам регистрации;
   - воронка: заявка опубликована → есть предложение → сделка создана → оплачена (PAID_HOLD) → принята (ACCEPTED) → выплата (SPLIT_PAYOUT).
4. **Данные** (`/v2/admin/data`): все модели Prisma базы `apps/web` — список моделей; для модели — таблица записей с поиском, фильтрами (поля-перечисления и булевы), постраничным выводом и сортировкой по дате создания; карточка записи со всеми видимыми полями и связями (ссылка на связанную запись; для связей «один ко многим» — число и ссылка на отфильтрованный список).
5. **Правка**: в карточке — форма с редактируемыми полями. Сохранение — Server Action → модуль `admin`: проверка прав, проверка правил поля, разбор значения по типу поля, затем в одной `transaction()`: `recordAudit` (`admin.record.updated`, `before`/`after` только изменённых полей) и условный `updateMany` по `id` и прежним значениям изменённых полей. Ноль строк — `CONFLICT` («запись изменили, обновите страницу»), транзакция откатывается вместе с аудитом.
6. **Реестр правил** — один файл кода `src/modules/admin/rules.ts`: модель → поле → `hidden` | `readonly` | `editable`, с правилами по умолчанию (ниже) и явными исключениями. Владелец после показа меняет только этот файл (через агента).

## Правила доступа к данным (по умолчанию)

Порядок применения: явное исключение в `rules.ts` → правило модели → правило поля по признаку. Сомнение — в сторону строгого.

**Скрыто совсем (`hidden`)** — поле не выбирается из базы (`select` строится только из видимых полей), не ищется, не фильтруется, не показывается и через связи:
- имена на `Enc`, `Hash`, `Last4` (ИИН/БИН, IBAN, сертификат, токены и коды: `iinEnc`, `iinHash`, `iinLast4`, `binIin*`, `signerIin*`, `payoutIban*`, `certIinLast4`, `tokenHash`, `codeHash`);
- ключи push-подписок и подобные секреты (`PushSubscription.p256dh`, `auth`, `endpoint`) — решение исполнителя спеки;
- явный список в `rules.ts` для полей с ПДн без признака в имени (исполнитель плана проходит схему и дописывает; тест ловит новое поле с `Enc`/`Hash`/`Last4`).

**Только чтение — вся модель** (`readonly`):
- `MoneyTransaction` (решение владельца 3), `AuditEvent` (журнал не правится), `PaymentWebhookEvent`, `Document`, `Signature`, `HandSignature` (юридический след);
- `User`, `Session`, `OtpCode` — источник правды о людях и сессиях — identity (ADR-013); правка в web разошлась бы с identity — решение исполнителя спеки;
- технические: `Job`, `RateLimitBucket`, `AiUsage`, `PushSubscription` — решение исполнителя спеки.

**Только чтение — поле по признаку** (в любой модели):
- `id`, `createdAt`, `updatedAt`, поля с `@updatedAt`;
- поля-статусы: тип — перечисление с именем на `Status` (`RequestStatus`, `DealStatus`, `OfferStatus`, `RegistrationStatus`, `KycStatus`, `InvitationStatus`, `MeasurementStatus`, `SiteMeasurementStatus`, `ProjectStatus`, `DepositStatus`, `ProposalStatus`, `DisputeStatus`, `MoneyTransactionStatus`, `DocumentStatus`, `JobStatus`, `VisualizationStatus`) — решение владельца 2;
- `DateTime`-поля моделей со статусной машиной (`Deal`, `Request`, `Offer`, `Dispute`, `Measurement`, `SiteMeasurement`, `Project`, `MeasureDeposit`, `PriceProposal`, `RequestInvitation`, `ExecutorProfile`): это отметки переходов (`signedAt`, `paidAt`, `hiddenAt` и т. п.); правка ломает переходы, раскрытие контактов (`Deal.signedAt`) и сроки — решение исполнителя спеки;
- `BigInt` — суммы в тиынах: модель денег заморожена (`computeDealMoney`), правка цены ломает её — решение исполнителя спеки;
- скалярные внешние ключи (поля из `@relation(fields: …)`): перепривязка записей ломает целостность — решение исполнителя спеки;
- `Json` и списки (`[]`) — в первой версии только чтение (нет безопасного редактора) — решение исполнителя спеки.

**Редактируемое (`editable`)** — всё остальное: строки, числа `Int`, булевы, перечисления не-статусы, `DateTime` моделей без статусной машины. Пример: названия и описания видов мебели, цены материалов, тексты профиля мастера, настройки платформы со скалярным значением.

## Не-цели

- Смена статусов любых сущностей (решение владельца 2) — только процессами и экранами оператора.
- Создание и удаление записей — решение исполнителя спеки; появится, если владелец попросит после показа (удаление — никогда для денег, аудита, документов).
- Базы Go-сервисов (`identity` и др.) — в первой версии нет: админка читает базу `apps/web`; люди и роли видны через проекцию `User` (только чтение) — решение исполнителя спеки.
- Блокировка людей, выдача ролей из интерфейса — нет (делает identity; позже — отдельной задачей через методы identity).
- Выгрузки CSV, графики — нет (статистика — числа и таблицы).
- Мобильная вёрстка как основная: админка — экран компьютера; на телефоне работает (таблица → карточки, как `TableOrCards` оператора), но не оптимизируется — решение исполнителя спеки.

## Анти-цели (провал, даже если «работает»)

- Хоть одно зашифрованное или хешированное поле или `*Last4` ИИН/IBAN уходит в браузер — в списке, карточке, связи, поиске, фильтре, ошибке валидации или в аудите.
- Оператор, мастер, покупатель или администратор без пройденного второго фактора видят хоть одну страницу или вызывают действие админки.
- Изменение применилось без записи аудита, или аудит записался без изменения.
- Подмена имени модели или поля в форме (`model=MoneyTransaction`, `field=status`, `field=iinHash`) приводит к изменению или чтению.
- Две одновременные правки одного поля: вторая молча затирает первую.

## Ограничения (CLAUDE.md)

- Тексты — только русские, только из `ru` (`src/i18n/ru/app/admin.ts`); компоненты — только `@/kit`; доступность (≥ 48 px, контраст, клавиатура).
- Каждый вход — zod (`action()`), затем `requireUser("ADMIN")` первой строкой; модуль сам проверяет роль ещё раз.
- Деньги — тиыны, `BigInt`, без float; журнал денег — единственный источник для денежной статистики.
- Сервис-владелец сам проверяет права: identity проверяет второй фактор и роль администратора в сессии.
- Миграции — руками (web: Prisma SQL; identity: goose SQL), Go — DoD (`go vet`, golangci-lint, buf lint, `go test`).
- `APP_ENV=prod` — сид стенда запрещён; администратор в prod — только `grant-admin` из терминала.

## Как это устроено (выбор исполнителя спеки)

- **identity**: `ROLE_ADMIN = 5` в `proto/senim/identity/v1`; миграция `0013_admin_role.sql` (CHECK ролей и активной роли допускают `ADMIN`; сотрудник `OPERATOR|MEASURER|ADMIN` — одна роль); `isStaff` включает `ADMIN`; второй фактор нужен ролям `OPERATOR` и `ADMIN` (`needsMfa(role)`), при этом переходы KYC и согласий остаются только за `OPERATOR`; `SeedUsers` допускает `ADMIN` с TOTP-секретом; подкоманда `grant-admin`.
- **web**: `Role.ADMIN` в Prisma (миграция `ALTER TYPE "Role" ADD VALUE 'ADMIN'`), проекция ролей, `STAFF_ROLES`, `homeFor` → `/v2/admin`, экран второго фактора — существующий `/v2/operator/mfa` принимает и администратора (решение исполнителя спеки: один экран, меньше кода), оболочка админа — вкладки «Статистика», «Данные», «Профиль».
- **Метаданные моделей**: рантайм Prisma 7 (`runtimeDataModel`) не несёт `isRequired`/`isList`/`@id`/`@default`, пакета `@prisma/internals` нет. Поэтому скрипт `scripts/admin-schema.ts` разбирает `prisma/schema.prisma` и пишет `src/modules/admin/schema.gen.ts` (модели, поля: имя, тип, вид scalar/enum/object, обязательность, список, `@id`, `@updatedAt`, поля связи); unit-тест сверяет файл с текущей схемой (устарел — падает) и с `Prisma.ModelName`.
- **Чтение** строит Prisma `select` только из видимых полей; поиск — `contains` (`mode: insensitive`) по видимым строковым полям; фильтры — только по видимым перечислениям и булевым; связи — тоже через правила связанной модели.
- **Сравнение при правке** — по прежним значениям изменённых полей (форма несёт их скрытыми полями), не по `updatedAt`: у части моделей его нет.

## Что открыто для владельца после показа

- Какие модели и поля закрыть (`hidden`/`readonly`) или открыть для правки — меняется в `rules.ts`.
- Нужны ли создание записей (например, вида мебели) и удаление (не для денег, аудита и документов).
- Нужны ли блокировка людей и управление ролями из админки (через identity).
- Какие ещё числа нужны в статистике.

## Готово, когда

- `identity grant-admin --phone …` делает человека администратором; он входит по SMS, подключает/вводит TOTP и попадает на `/v2/admin`; без второго фактора — экран второго фактора, действия — `MFA_REQUIRED`.
- Оператор на `/v2/admin…` — отказ (нет роли), в меню оператора админки нет.
- Статистика показывает числа из базы, деньги — из журнала денег.
- Любая модель открывается списком и карточкой; скрытых полей нет ни в HTML, ни в данных RSC.
- Правка редактируемого поля пишет аудит с `before`/`after` и применяется; правка запрещённого поля, подменённого в форме, — `FORBIDDEN` без изменений и без аудита; одновременная правка — `CONFLICT` у второго.
- Полный `npm run check`, Go DoD и e2e администратора — зелёные.
