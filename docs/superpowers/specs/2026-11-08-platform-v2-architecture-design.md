# «Сенім» v2: микросервисная платформа — проектный документ

Дата: 08.11.2026. Статус: **утверждён владельцем 08.11.2026** (решения раздела 12 — все).

**Где ведётся [владелец]:** v2 — **отдельный репозиторий**; текущий репозиторий `mvp-scale-arna` продолжает получать обновления (демо для банков). Заменит ли v2 демо — решают основатели. Срока нет: качество важнее даты [владелец]. Как переносить обновления из текущего репозитория в v2 — раздел 9.1.
Связанные документы: `CLAUDE.md` (инварианты), ADR-009 (модель денег), `docs/legal/2026-11-07-legal-research.md`, `docs/legal/money-and-dispute-reminders.md`, `docs/bank/04-security-and-data.md`. Фронтенд — отдельный проектный документ (готовится по макетам).

Пометки: **[владелец]** — решение владельца; **[моё]** — решение автора документа, владелец может его оспорить; **[строителю]** — оставлено на усмотрение исполнителя.

## 1. Зачем

«Сенім» перестаёт быть одним Next.js-приложением. Ядро безопасной сделки (сделка, деньги на эскроу в банке, акт, спор, журнал денег и аудита) должно стать **самостоятельным движком**, которым потом пользуются другие отрасли и, в перспективе, государство **[владелец]**. Мебельная площадка — первая вертикаль поверх этого ядра.

Отсюда требования владельца: надёжно, безопасно, быстро, мало памяти; микросервисы; gRPC между сервисами; балансировщик нагрузки **[владелец]**. Строим «сразу как будет потом» в отдельной ветке, демо на `main` (Vercel) живёт для банков **[владелец]**.

## 2. Цели, не-цели, анти-цели

**Цели**
1. Паритет с текущим продуктом (ТЗ MVP v1.0, `docs/TZ_COMPLIANCE.md`) на новой архитектуре: все сценарии e2e (`e2e/*.spec.ts`) проходят против v2.
2. Ядро сделки (`deal`) ничего не знает о мебели и пригодно для другой вертикали без изменения кода.
3. Готовность к облаку в РК без переделок: всё в контейнерах, PostgreSQL, S3-совместимое хранилище, никаких привязок к Vercel в бэкенде.
4. Закрыты блокеры безопасности из ревью 07.11.2026 (раздел 8).
5. Готовность к будущему госстатусу: SBOM, воспроизводимая сборка, журналы, пригодные для выгрузки в ОЦИБ/SIEM, чистые права на код.

**Не-цели (сейчас)**
- Смена модели денег и порядка спора — заморожены до переговоров с банками (OPEN_QUESTIONS №64–65) **[владелец]**.
- Выбор облака в РК, реальные SMS, SIGEX, банк с API — позже **[владелец]**.
- Нативные мобильные приложения — пока PWA **[владелец]**.
- Перенос реальных данных: на v2 стартуем с чистой базой и демо-сидом.

**Анти-цели (провал, даже если «работает»)**
- Деньги клиентов проходят через счёт ТОО — в коде, текстах или схемах.
- Распределённые транзакции «на честном слове»: изменение статуса сделки и запись в журнал денег оказались в разных базах без гарантии согласованности.
- Двойной эффект от повторного запроса или повторной доставки события.
- Сервис доверяет вызывающему без проверки прав («внутри сети — значит можно»).
- Одному разработчику невозможно поднять всё локально одной командой.

## 3. Ограничения

- Все инварианты `CLAUDE.md` («Продуктовые инварианты» и Definition of Done) остаются в силе и переносятся на Go: тиыны в `int64`, одна функция расчёта денег, таблица переходов, тест на каждый разрешённый и запрещённый переход на реальной БД, аудит в той же транзакции, конкурентные переходы через условный `UPDATE` или `SELECT … FOR UPDATE`.
- Тексты интерфейса — только в вебе (`src/i18n/ru.ts`); сервисы возвращают коды ошибок, не тексты.
- Разработчик — один человек с ИИ-агентами **[владелец]**: всё поднимается одной командой, контракты генерируют код, а не пишутся дважды.
- Бюджет тестового стенда — бесплатно **[владелец]**.
- Реальные персональные данные — только в ЦОД в РК (Закон № 94-V, ст. 12 п. 2). Любой стенд вне РК — только вымышленные данные.

## 4. Целевая архитектура

```
Браузер / PWA
   │ HTTPS
   ▼
edge (Envoy) ── TLS, лимиты, заголовки безопасности
   │ HTTP
   ▼
web (Next.js 16, TypeScript) ── интерфейс + BFF: сессия, тексты, формы
   │ gRPC (HTTP/2, mTLS)
   ▼
mesh-gateway (Envoy) ── балансировка gRPC по запросам, ретраи, тайм-ауты, маршрут по имени gRPC-сервиса
   │
   ├── identity     ├── deal        ├── marketplace   ├── operator
   ├── documents    ├── files       ├── notify        └── audit
   │
   ├── PostgreSQL (своя база и свои роли у каждого сервиса)
   ├── NATS JetStream (события между сервисами)
   ├── S3-совместимое хранилище (MinIO локально)
   └── OpenTelemetry Collector → Grafana (логи, метрики, трейсы)
```

Почему отдельный Envoy для gRPC **[моё]**: gRPC держит одно долгое HTTP/2-соединение, и балансировщик уровня TCP отправит весь трафик на один экземпляр. Envoy балансирует по запросам, маршрутизирует по префиксу пути (`/senim.deal.v1.DealService/…` → кластер `deal`), даёт тайм-ауты, ретраи только идемпотентных методов и ограничение отказов. Один и тот же конфиг работает в docker compose и в Kubernetes.

### 4.1. Сервисы

| Сервис | Язык | Владеет данными | Делает | Не делает |
|---|---|---|---|---|

| **identity** | Go | User, роли, Session, OtpCode, ИИН/БИН, IBAN (шифрованные), KYC-статус, согласия на ПДн, 2FA операторов | вход по коду, сессии, выдача внутреннего токена, профиль личности, согласия | доставку кодов (зовёт `notify`) |

| **marketplace** — мебель | Go | Request, Offer, PriceProposal, ExecutorProfile, портфолио, чат, справочник материалов, калькулятор | заявки, отклики, торг, выбор исполнителя → создание сделки в `deal`, маска контактов в чате | деньги |
| **documents** | Go | Document, Signature, HandSignature, версии, sha256 | PDF оферты, акта, выписки; ЭЦП (mock → Kalkan через `gokalkan` → SIGEX); проверка подписи на сервере | решение о статусе сделки (сообщает событием) |
| **files** | Go | метаданные файлов | загрузка по подписанной ссылке, проверка типа по байтам, пережатие фото, HEIC, удаление EXIF, антивирусная проверка PDF | — |

| **operator** | Go | настройки площадки, проекции для отчётов, очередь ручных операций | бэк-офис: модерация, KYC, ручные подтверждения банка, решения по спорам, отчёты и сверка — вызывая сервисы-владельцы | менять чужие данные напрямую |

Отдельный сервис оператора — **[владелец]**. Принцип: `operator` — оркестратор и владелец только своих данных; любое изменение сделки он делает вызовом `deal`, модерацию профиля — вызовом `marketplace`, и права проверяет сервис-владелец.

### 4.2. Связь сервисов

- **Синхронно — gRPC** **[владелец]**. Контракты — protobuf в `proto/senim/<сервис>/v1/*.proto`, проверка `buf lint` и `buf breaking` в CI. Из одних `.proto` генерируются сервер на Go и клиент на TypeScript для `web` **[моё]**. Реализация — `connect-go` и `@connectrpc/connect` (говорят протоколом gRPC) или `grpc-go` **[строителю]**; обязательно — протокол gRPC поверх HTTP/2 через Envoy.
- **Асинхронно — события через NATS JetStream** **[моё]**: лёгкий, написан на Go, хранит события, повторяет доставку. Каждое событие — protobuf из `proto/senim/events/v1`.
- **Outbox**: сервис пишет событие в свою таблицу `outbox` **в той же транзакции**, что и изменение данных; отдельный цикл публикует его в NATS. **Inbox**: получатель записывает `event_id` и обрабатывает событие один раз. Повторная доставка не даёт второго эффекта.
- **Идемпотентность вызовов**: каждый изменяющий gRPC-метод принимает `idempotency_key`; сервис хранит ключ и результат. Envoy ретраит только методы, помеченные идемпотентными.
- **Тайм-ауты**: дедлайн задаёт `web` (по умолчанию 5 с) и передаётся дальше; ни одного вызова без дедлайна.

### 4.3. Сквозные сценарии (как было в одной транзакции → как будет)

| Сценарий | Сейчас (монолит) | В v2 |
|---|---|---|
| Выбор отклика → сделка | `requests` вызывает `deal-core` в одной транзакции, заявка → CONTRACTING | `marketplace` вызывает `deal.CreateDeal(idempotency_key = offer_id)`; получив `deal_id`, в своей транзакции переводит заявку в CONTRACTING. Сбой между шагами — повтор с тем же ключом даёт ту же сделку |
| Подписи оферты → `signedAt`, раскрытие контактов | `documents` → порт `deal-core` | последняя подпись: `documents` **синхронно** вызывает `deal.RecordOfferSigned(deal_id, document_id, idempotency_key)`; `deal` проверяет состояние под блокировкой и либо фиксирует «оферта заключена», либо отказывает (сделка отменена) — тогда подпись не завершается и пользователь видит причину. `marketplace` открывает контакты по событию `OfferConcluded` от `deal` **[моё]** |
| Акт подписан всеми → ACCEPTED → выплата | `documents` → `deal-core.processDealMoney` сразу после коммита | так же синхронно: `deal.RecordActSigned(...)`; `deal` атомарно: ACCEPTED + операции журнала + outbox или отказ (открыт спор, сделка не в READY). Источник истины о статусе — только `deal` **[моё]**; исполнение провайдером — задачей в `deal` |
| Закрытие или отмена заявки по итогу сделки | порт `requests` | `deal` публикует `DealClosed{outcome}`; `marketplace` переводит заявку (CLOSED/CANCELLED) |
| Ручное подтверждение банка (`manual`) | экран оператора → `payments` | `operator` → `deal.ConfirmManualOperation` (номер, дата, файл из `files`); `deal` проверяет права и состояние |
| Решение спора | оператор → `deal-core` | `operator` → `deal.ResolveDispute`; порядок исполнения не меняется (OPEN_QUESTIONS №65) |
| Аудит | `recordAudit()` в той же транзакции | каждый сервис пишет событие аудита в свой outbox в той же транзакции; `audit` принимает и сцепляет хэши |

Статусы, переходы, формулы денег и тексты переносятся **без изменений** (ADR-009).

### 4.4. Вход и права

- Браузер ↔ `web`: cookie `__Host-senim_session` (httpOnly, Secure, SameSite=Lax), тайм-аут простоя и абсолютный срок **[моё]**: 30 мин простоя и 7 дней для пользователей, 8 ч для операторов.
- `web` → сервисы: на каждый запрос `web` получает у `identity` короткий внутренний токен (подпись Ed25519, срок 5 мин, кэш в `web`) с `user_id`, активной ролью, ролями, признаком 2FA и `session_id`. Каждый сервис проверяет подпись по ключам `identity` (JWKS) и **сам решает**, можно ли действие (аналог `requireUser(...роли)` плюс проверка владения объектом).
- Сервис ↔ сервис: mTLS с удостоверением сервиса; при вызове от имени пользователя токен пользователя передаётся дальше.
- Операторы: обязательная вторая ступень входа — TOTP или WebAuthn **[моё]**; для операций с деньгами (`manual`-подтверждения, повтор операции, решение спора) — повторный ввод второй ступени.

## 5. Хранение данных

- **PostgreSQL 17**, один кластер, у каждого сервиса **своя база**. Две роли на сервис: `<svc>_owner` (миграции, владеет таблицами) и `<svc>_app` (только `SELECT/INSERT/UPDATE` на нужные таблицы, без `TRUNCATE`, без DDL). Сервис другого сервиса не видит.
- Миграции — SQL-файлы (`goose` или `atlas` **[строителю]**), запуск отдельной задачей с ролью `owner` до выката, не при сборке.
- **Деньги** — `BIGINT` тиыны; CHECK формулы денег и триггеры только на добавление для журнала денег и аудита переносятся из текущих миграций.
- **Персональные данные** сосредоточены в `identity`: ИИН/БИН, IBAN, ФИО, телефон. Шифрование AES-256-GCM с идентификатором ключа в формате (`v2.<kid>.…`), ключ данных под мастер-ключом (envelope; локально — ключ из env, в облаке — KMS), задача перешифрования при смене ключа. Для поиска — HMAC с отдельным ключом; для OTP — свой ключ. Остальные сервисы хранят `user_id` и, где нужно для показа, последние 4 символа.
- Адрес и GPS сдачи — шифруются в `marketplace` и `deal` тем же механизмом.
- **Файлы** — S3-совместимое хранилище (MinIO локально), приватные корзины, подписанные ссылки, шифрование на стороне сервера.
- **Сроки хранения** — задача очистки в каждом сервисе: OTP, сессии, лимиты, сырые вебхуки. Конкретные сроки — по политике ПДн, когда её утвердит юрист; до этого — значения в конфиге с безопасными умолчаниями **[моё]**.
- **Резервные копии** — `pg_dump`/WAL-архив в S3 по расписанию, проверочное восстановление раз в неделю на стенде **[моё]**.
- **Согласия на ПДн** — запись с версией текста, целями, временем, каналом подтверждения; отзыв запускает процесс удаления (Закон № 94-V, ст. 8; см. исследование A.7–A.8).

## 7. Платформа разработки и развёртывания

- **Монорепозиторий** **[моё]**: `apps/web` (текущий Next.js), `services/<имя>` (Go), `proto/`, `deploy/compose`, `deploy/k8s`, `go.work`. Общие Go-пакеты (`pkg/money`, `pkg/authz`, `pkg/outbox`, `pkg/pii`, `pkg/audit`, `pkg/config`) — только инфраструктура, не бизнес-логика.
- **Go** 1.25+ **[строителю — актуальную стабильную]**: `pgx` + `sqlc` (SQL пишется руками, типы генерируются), `testcontainers-go` для интеграционных тестов на реальной БД, `pgregory.net/rapid` для property-тестов денег, OpenTelemetry SDK, `log/slog` с маской ПДн.
- **Локально — одна команда** (`make up` или `npm run v2:up` **[строителю]**): docker compose поднимает Postgres, NATS, MinIO, ClamAV, Envoy (edge и mesh-gateway), OTel + Grafana, все сервисы и `web`; сид демо-данных идёт через gRPC-API сервисов, а не прямыми вставками.
- **Профили compose и бюджет памяти** **[моё]**: машина разработчика — 32 ГБ, 16 потоков. Профиль `core` (Postgres, NATS, MinIO, Envoy, сервисы, `web`) — цель ≤ 3 ГБ; профиль `full` добавляет ClamAV и Grafana-стек (≤ 6 ГБ). Цель на Go-сервис — ≤ 64 МБ в простое; измеряется и выводится в отчёт шага.
- **Kubernetes** — манифесты или Helm под k3s и управляемый Kubernetes облака РК; образы `distroless` (у `documents` — `debian-slim` из-за cgo и библиотеки Kalkan).
- **CI** (GitHub Actions): `buf lint/breaking`, `go vet`, `golangci-lint`, `go test` с testcontainers, `govulncheck`, сборка образов, SBOM (`syft`), проверка уязвимостей образов, typecheck/lint/test `web`, e2e Playwright против docker compose.
- **Наблюдаемость**: трассировка сквозь `web` → сервисы → NATS; метрики RED на каждый метод; health-эндпоинты (`/healthz`, `/readyz`) у каждого сервиса; логи JSON в stdout → Collector.

## 8. Безопасность — что закрываем в v2 (из ревью 07.11.2026)

| Было | В v2 |
|---|---|
| Оператор входит только по SMS-коду, сессия 30 дней | 2FA (TOTP/WebAuthn), сессия 8 ч, повторная 2FA на денежные действия |
| Сид создаёт демо-оператора в prod | сид отказывается при `APP_ENV=prod` |
| `env.ts` пропускает слабые секреты, одинаковые ключи, `local`-хранилище в prod | строгая проверка конфига в каждом сервисе |
| Одна роль БД для миграций и приложения | `owner` / `app` на каждую базу |
| Нет CSP со `script-src` | CSP с nonce в `web`, заголовки безопасности на edge |
| IP — правый адрес `x-forwarded-for` | число доверенных прокси в конфиге; лимиты по IP мягче, плюс по номеру и устройству |
| Один ключ шифрования без идентификатора | envelope + `kid` + перешифрование |
| Открытым текстом адрес, GPS | шифрование полей |
| Нет очистки OTP, сессий, вебхуков | задачи сроков хранения |
| PDF без антивируса | ClamAV до прикрепления |
| Нет журнала чтения ПДн (KYC, PDF с ИИН, CSV) | событие аудита на чтение |
| Нет хэш-цепочки журнала | `prev_hash` в `audit`, ежедневная фиксация корня |
| Логи только в stdout | Collector → хранилище логов; готовность к выгрузке в ОЦИБ/SIEM |
| Транзитивные уязвимости `@vercel/blob` | бэкенд без Vercel-пакетов; `govulncheck` и проверка образов в CI |

## 9. Как переходим (в отдельном репозитории v2)

### 9.1. Новый репозиторий и обновления из текущего **[моё]**

- Локально — `D:\senim-platform` (имя и удалённый репозиторий на GitHub создаёт владелец; агент не пушит).
- Текущий Next.js переносится в `apps/web` **с историей** через `git subtree add --prefix=apps/web <путь к mvp-scale-arna> main`. Обновления демо потом подтягиваются `git subtree pull --prefix=apps/web … main`; чем дальше `apps/web` уходит от `main`, тем больше ручного слияния — поэтому подтягиваем часто и небольшими порциями.
- Правовые документы (`docs/legal/`) и этот документ живут в v2 в `docs/`; правовые документы также остаются в текущем репозитории.

### 9.2. Шаги

1. **Каркас**: монорепозиторий, proto, docker compose со всей инфраструктурой, Envoy, OTel, CI, пустые сервисы с health-проверками.
2. **identity** → `web` переходит на вход и сессии через gRPC.
3. **deal** (ядро, деньги, споры, `mock` и `manual`) — перенос тестов статусной машины и денег один к одному: каждый текущий `*.int.test.ts` этой зоны получает Go-аналог.
4. **documents** (PDF с кириллицей, ГОСТ-вёрстка, подписи), **files**.
5. **marketplace** (заявки, отклики, торг, чат, профили, справочник).
6. **notify** (Telegram Gateway), **operator**, **audit**.
7. Удаление перенесённых модулей из `apps/web/src/modules`; e2e 65/65 против v2.

Данные на время перехода **[моё]**: v2 стартует с чистой базой и демо-сидом, текущие данные не переносятся. Сервисы с первого дня работают каждый в своей базе, связи между сервисами — только по идентификаторам, без внешних ключей. Модули `web`, которые ещё не перенесены, работают на старой схеме Prisma в отдельной базе и после переноса своей зоны выключаются; синхронизацию старых и новых данных не пишем. Поэтому:
- после каждого шага зелёные unit- и интеграционные тесты сервиса и `web`;
- e2e обязаны быть зелёными в двух контрольных точках — после шага 3 (вход + сделка + деньги) и в конце; между ними e2e затронутых зон могут временно не проходить.

Фронтенд **[моё]**: новый интерфейс делается параллельно в той же ветке. Экраны вызывают Server Actions, а Server Actions внутри переключаются с модулей на gRPC-клиенты — это разные слои, работа не пропадает. e2e переписываются вместе с новыми экранами.

## 10. Тестовый стенд

- **Основной — локально** одной командой **[владелец]**.
- **Бесплатный внешний стенд — по возможности** **[владелец]**. Факты на 08.11.2026: бесплатные PaaS (Render, Railway, Koyeb) не подходят для 10 контейнеров с базой, брокером и gRPC — засыпают, срезаны или стали платными. Vercel годится только для `web`. Реально бесплатный вариант — виртуальная машина Oracle Cloud Always Free (Arm; по свежим сообщениям лимит сокращён до 2 ядер и 12 ГБ, проверить в консоли) с k3s **[моё, ⚠]**. Только вымышленные данные (стенд вне РК).
- Вариант для `web`: превью-деплой ветки на Vercel, бэкенд — на ВМ за Envoy по HTTPS **[строителю, если ВМ будет]**.

## 11. Оставлено строителю

`connect-go` или `grpc-go`; `goose` или `atlas`; структура пакетов внутри сервиса; формат конфигов Envoy (статический или xDS); Helm или kustomize; инструмент PDF на Go (вёрстка ГОСТ, шрифт Tinos, кириллица) — при условии совпадения сумм до тиына с журналом и проверок e2e; точные имена событий и методов.

## 12. Решения автора документа (на проверку владельцу)

1. Отдельный Envoy-шлюз для gRPC внутри (mesh-gateway) плюс Envoy на входе.
2. NATS JetStream как брокер; outbox и inbox у каждого сервиса.
3. `deal` объединяет статусную машину, журнал денег и споры — потому что они меняются в одной транзакции.
4. ПДн личности сосредоточены в `identity`; envelope-шифрование с `kid`.
5. Внутренний токен Ed25519 на 5 минут + mTLS; каждый сервис сам проверяет права.
6. 2FA и повторная 2FA на денежные действия для операторов.
7. Монорепозиторий; Go + pgx + sqlc; Kubernetes в проде, docker compose локально.
8. Сроки сессий: 30 мин простоя / 7 дней; операторы — 8 ч.
9. Бесплатный внешний стенд — Oracle Cloud Always Free + k3s, только вымышленные данные.
10. Последние подписи оферты и акта — синхронный вызов `deal`; `deal` может отказать, источник истины о статусе — только он.
11. Переход без синхронизации данных: чистая база, своя база у сервиса, e2e зелёные в двух контрольных точках.
12. Фронтенд — параллельно в той же ветке.
13. Профили compose `core` и `full`, цель ≤ 64 МБ на Go-сервис.
