`SKILL.md` (раздел «Then Make it Right») требует трёх инструментов — `crapper`, `dryer`, `mutator`. Их нет в окружении, поэтому здесь — эквиваленты на стандартных пакетах (решение владельца, [OPEN_QUESTIONS №2](../OPEN_QUESTIONS.md)).

| Скилл | Команда | На чём | Отчёт (не в git) |
|-------|---------|--------|------------------|
| Crapper | `npm run quality:crap` | `scripts/quality/crap.mjs`: покрытие `@vitest/coverage-v8` + сложность по AST `typescript` | `reports/quality/crap.json`, таблица в консоли |

## Crapper — `npm run quality:crap`

```bash
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:5442/senim_test_quality npm run quality:crap
npm run quality:crap -- --reuse                       # без прогона тестов, по готовому покрытию
npm run quality:crap -- --only src/modules/deal-core  # только файлы с этим префиксом (можно несколько)
npm run quality:crap -- --check                       # код выхода 1, если есть функции с CRAP ≥ порога
npm run quality:crap -- --threshold 15                # другой порог (по умолчанию 10)
```

**Формула.** `CRAP(f) = comp² × (1 − cov)³ + comp`.

- `comp` — цикломатическая сложность функции: 1 + `if`, `?:`, `case` с условием, `for`/`for…of`/`for…in`, `while`, `do`, `catch`, `&&`, `||`, `??` (и `&&=`, `||=`, `??=`). Как у правила ESLint `complexity`, но без `?.` и параметров по умолчанию. Вложенные функции (колбэки, стрелки) — отдельные функции, их ветки родителю не засчитываются.
- `cov` — доля покрытых операторов (statements) тела функции без вложенных функций, по istanbul JSON от `@vitest/coverage-v8`. Функция без операторов (`() => x`) — по факту вызова.

**Покрытие** собирается полным прогоном Vitest (unit + integration), поэтому нужна `TEST_DATABASE_URL`. Своя база — чтобы не мешать другим прогонам; `senim_test` и рабочую базу не используйте. Анализируется `src/**/*.{ts,tsx}` без `src/generated`, `src/i18n`, тестов и `.d.ts`.

**Как читать.** Таблица: CRAP, сложность, покрытие операторов в процентах, `файл:строка` и имя функции (у анонимных — `вызов(…) callback`). Ниже — сводка по зонам: сколько функций выше порога в логике (`.ts`) и в компонентах (`.tsx`). Звёздочка `*` перед файлом — он изменён после начала замера (в дереве работает кто-то ещё): строки не совпадают с картой покрытия, его число недостоверно до следующего прогона. Если часть тестов упала, скрипт предупреждает: покрытие их модулей занижено.

**Порог — 10.** Что из этого следует:

- функция с полным покрытием проходит, только если её сложность ≤ 9 (при cov = 1 CRAP = comp) — такие функции надо разбивать;
- функция без покрытия проходит, только если сложность ≤ 2 (3² + 3 = 12) — такие надо покрывать тестами или упрощать;
- `switch` на 8 и больше веток сам по себе даёт ≥ 9: каждая ветка, вынесенная в функцию, снижает сложность на её условия, но не на `case`. Разумно, если ветки делают разное; таблица переходов вместо `switch` — лучше (как в `deal-core/transitions.ts`).

## Dryer — `npm run quality:dup`

Настройки `.jscpd.json`:

| Параметр | Значение | Почему |
|----------|----------|--------|
| `path` | `src` | только код приложения |
| `ignore` | `src/generated/**`, `src/i18n/**`, `*.test.ts(x)`, `*.int.test.ts` | сгенерированный клиент Prisma, тексты (их повторы — это одинаковые фразы, а не логика) и тесты (подготовка данных похожа по природе) |
| `format` | `typescript`, `tsx` | — |
| `mode` | `mild` | пробелы и переводы строк не влияют, комментарии — тоже |
| `minTokens` | 50 | меньше — ловятся одинаковые импорты и сигнатуры; 50 токенов — это 4–6 строк настоящей логики |
| `minLines` | 5 | однострочные совпадения (вызов с похожими аргументами) — не дублирование |
| `similarity` | 0,8 | **ранг 0,8 из SKILL.md**: jscpd сравнивает синтаксические деревья функций, где локальные имена и литералы заменены метками, а вызовы и операторы сохранены; оценка — доля общих поддеревьев. Пара функций со сходством ≥ 0,8 — «похожий клон» (Type-3) |
| `minNodes` | 40 | меньше — совпадают любые две короткие функции из `return <JSX/>` |

Отчёт показывает два вида находок: **точные клоны** (Type-1, одинаковые токены от 50 штук) и **похожие** (`similar (ast) ~0.83` — сходство деревьев). И те, и другие устраняются: общая функция, компонент или таблица данных.

## Mutator — `npm run quality:mutate`

```bash
npm run quality:mutate                                        # набор по умолчанию (ниже)
npm run quality:mutate -- --mutate src/modules/companies/mask.ts   # свой набор, через запятую
```

По умолчанию мутируется чистая логика, где ошибка стоит денег или статуса:

- статусные машины и «что дальше»: `deal-core/transitions.ts`, `next-step.ts`, `stage-plan.ts`, `requests/transitions.ts`;
- деньги: `deal-core/retry-policy.ts`, `payments/fees.ts`, `escrow-status.ts`, `reconcile-entries.ts`, `webhook-signature.ts`, `modes.ts`;
- маска контактов, ИИН/БИН, проверки ввода: `companies/mask.ts`, `platform/kz-id.ts`, `platform/validation.ts`;
- правила мебельной вертикали: `verticals/furniture/segment.ts`, `stage-templates.ts`.

**Как устроено.** Stryker копирует проект в `.stryker-tmp/` (внутри репозитория: `node_modules` находится подъёмом по каталогам, ссылку на него не создаём — удаление ссылки на Windows уже стирало пакеты), прогоняет **только unit-проект** Vitest (`scripts/quality/vitest.unit.config.mjs`) в режиме `related` — тесты, которые импортируют мутируемый файл. Интеграционные тесты под Stryker не запускаются: им нужна своя база на каждый из 4 параллельных процессов, а чистая логика проверяется unit-тестами полностью. Набор по умолчанию проходит примерно за 3 минуты. Если Stryker не смог удалить песочницу (на Windows воркеры держат файлы кэша vite), каталог `.stryker-tmp/sandbox-*` можно удалить вручную: ссылок в нём нет; `tsc` и `eslint` его не видят.

**Как читать.** `killed` — тест упал на мутанте (хорошо); `survived` — мутант пережил все тесты (нет проверки этого поведения или код лишний); `no cov` — строку не выполняет ни один тест. Mutation score = убитые / все. В HTML-отчёте у каждого выжившего видна замена. Пороги в конфиге: ≥ 90 % — хорошо, < 75 % — плохо; сборку не ломает.

**Эквивалентные мутанты** — замены, которые не меняют поведения (например, `>` → `>=` при выборе максимума из равных). Их не «убивают», а оставляют с пометкой; если код можно упростить так, чтобы мутант исчез, — упрощают.

Доведено до CRAP < 10 (разбиение и/или тесты): решение спора (`resolveDispute`, сложность 26), показ сделки, хук оплаты, «что дальше», правило повтора операций, итог операции банка и событие операции из вебхука (путь не покрывал ни один тест — добавлены интеграционные), проверка env (21), шаги подписи и цель фокуса, `pickFields` (21), `toDraft`, `toCm`, `subjectDetails`, `sniffType`, `buildScenario`, `decideFileAccess`, `runVisualization`, CSV отчёта, `action()` с ошибками полей, тип файла загрузки, условия замера.

**Осталось `.ts` — 38:**

- **Зоны параллельных агентов — 20** (в этом заходе не трогались): `modules/requests` — 7 (`flows.ts` ×2, `drafts.ts` ×3, `schema.ts` `applyStep`, `transitions.ts`); `modules/identity` — 2 (`signerIssues`, `recordPersonIdentity`); `app/_shell/nav.ts` — 1; охрана страниц `app/requests/_parts/guard.ts` ×2 и `app/operator/_lib/guard.ts` — 3 (переделываются под роли); `modules/companies` `identity-mode.ts`, `chat-policy.ts` — 2 (режим имени исполнителя, №6, в работе); `src/demo` — 5 (сид меняется вместе с ролями, его тесты падали по таймауту).
- **Артефакты замера — 7**: файлы менялись другими во время прогона или их тесты падали из-за чужой миграции (`operator/scenario.ts` ×2, `audit/index.ts` ×2, `deal-core/queries.ts` ×3 — покрыты при зелёных тестах). Теперь такие файлы помечаются `*`.
- **В зонах этого захода — 11**, нужны инструменты, которых в проекте нет: обработчики маршрутов `GET`/`PUT` (`api/cron/run`, `api/files/*`, `operator/report/csv`) — 4, хуки React (`useRunAction`, `useActionForm`) — 2, Server Actions (`notifications/actions`, `requests/actions`) — 2, DOM (`ui/focus.ts`, загрузка через XHR в `uploader/transfer.ts`) — 2, `report.reconcileOrNull` (сбой выписки банка) — 1.

**Компоненты `.tsx` — 174.** Экраны и компоненты проверяются сквозными тестами Playwright, а их покрытие Vitest не видит; тестов компонентов (jsdom + Testing Library) в проекте нет. При нулевом покрытии компонент проходит порог только со сложностью ≤ 2, поэтому разбиением это не решается. Варианты на решение владельца: (1) добавить проект Vitest с jsdom и `@testing-library/react` и покрывать ветки компонентов; (2) собирать V8-покрытие прогона Playwright и сливать с покрытием Vitest; (3) считать порог CRAP только для `.ts`, а для `.tsx` — отчёт без порога.
