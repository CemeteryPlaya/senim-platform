## 2. Решения владельца и основателей (зафиксированы)

### 2.1. Деньги

1. **Формулы ТЗ п. 6 — сразу.** Цена по оферте X. Покупатель платит X + защита 2%. Мастер получает X − гарантия 4%. Доход платформы — разница, 6% от X.
2. **Все суммы — в тиынах (`Int`/`BigInt`), никакого float.** Округление: защита 2% — вверх до тиына, выплата мастеру — вниз до тиына, доход платформы = оплачено − выплата (поглощает округление). Инвариант «оплачено = выплата мастеру + доход платформы» до тиына — автотест, в том числе property-based (fast-check) на случайных X.
   - Формулировку ТЗ про округление «вверх в пользу покупателя» запиши в `OPEN_QUESTIONS`: округление защиты вверх не в пользу покупателя. Реализуй правило одной функцией, чтобы его можно было поменять в одном месте.
3. **Термины ТЗ п. 5 в интерфейсе.** Покупатель: «Защита сделки (2%)», смета «Стоимость заказа · Защита сделки (2%) · Итого к оплате». Мастер: «Гарантия оплаты и клиента (4%)», смета «Сумма заказа · Гарантия оплаты (4%) · К выплате». Суммы и проценты показываются до подтверждения оплаты. Строки, которые раньше были скрыты (например, на экране по макету стр. 18), теперь показываются с этими терминами.
4. **Слова «комиссия» и «эскроу» в интерфейсе запрещены.** Вместо «эскроу» — «деньги в банке под защитой». Слово «эскроу» остаётся только в оферте, договорах, `docs/` и у оператора.
   - Агент раньше сделал «эскроу» центральным словом — вычисти его из всех текстов `src/i18n` для покупателя и мастера.
   - Добавь тест, который падает, если в текстах покупателя и мастера встречаются «эскроу» или «комисси».
5. **Экран денег — первый блок карточки сделки (ТЗ п. 4.1):**
   - CREATED: серый блок «Ожидает оплаты — деньги ещё не внесены»;
   - PAID_HOLD / IN_PROGRESS / READY: зелёный блок «N ₸ — под защитой банка. Недоступны мастеру до вашей подписи акта», дата резервирования и номер операции, иконка замка;
   - открыт спор: жёлтый блок «Выплата заморожена до решения спора»;
   - ACCEPTED / SPLIT_PAYOUT: «Сделка завершена. Выплачено мастеру: … · Защита сделки: …».
   Всё, что сейчас стоит наверху (фото, исполнитель, сроки, гарантия, шкала, «Осталось N дней»), переносится в раскрывающийся блок «Подробнее о заказе» под блоком денег.
6. **Зеркальный блок у мастера (ТЗ п. 4.2):** уже в карточке заявки — «Деньги покупателя будут зарезервированы в банке до начала работ»; после оплаты — «Деньги зарезервированы: N ₸ — получите после подписания акта покупателем».
7. **Два отдельных таймлайна:** «История денег» (тап по блоку денег: зарезервировано → удержано на время спора → выплачено, со ссылками на документы; печатаемая выписка PDF) и общая «История событий».
   - Блок денег и история денег строятся **только из журнала транзакций**, не из статуса заказа: деньги первичны, статус вторичен.
8. **Уведомление обеим сторонам на каждое изменение денег — web push.** Плюс in-app уведомление.

### 2.2. Сделка

1. **Статусная машина ТЗ п. 9:** `CREATED → PAID_HOLD → IN_PROGRESS → READY → ACCEPTED → SPLIT_PAYOUT`, переходы строго последовательные, перескоки запрещены в коде. Обкатываем как есть, доработки — потом.
2. **Оплата одна.** Покупатель вносит всю сумму X×1,02 в начале (PAID_HOLD). Мастер получает полную выплату X×0,96 одним платежом в конце: после сдачи (READY) и подписания акта покупателем (ACCEPTED → SPLIT_PAYOUT). Авансов нет. Оплаты по этапам и акты этапов из платёжного пути убираются. Этапы можно оставить только как необязательные фото-отчёты мастера «Ход работ» в ленте сделки, без денег и актов.
3. **Торг по ТЗ:** до оферты стороны обмениваются встречными ценами в чате заказа. Акцепт фиксирует X и порождает оферту. Торг — отдельная сущность (раунды предложений: кто, сумма, когда, статус), а не текст в чате.
4. **Подписание.** Оферта и акт приёмки подписываются:
   - а) собственноручной подписью: при подписании открывается холст, человек рисует подпись пальцем или мышью. Изображение встраивается в PDF и хранится вместе с хэшем документа, временем, IP и устройством;
   - б) дополнительно ЭЦП обеих сторон через существующий `SignatureProvider` (пока мок).
   Оферту подписывают обе стороны. Акт подписывает покупатель (собственноручно и ЭЦП); подпись мастера на акте — ЭЦП. Нужна ли и мастеру собственноручная подпись на акте — вопрос в `OPEN_QUESTIONS`; сделай её настраиваемой.
5. **READY:** фото результата обязательно. GPS — мягкая проверка: при сдаче запрашивается геолокация браузера, считается расстояние до адреса заказа (haversine). Больше 500 м — предупреждение, а не блокировка. Расстояние и признак «в радиусе» сохраняются и попадают в акт.
   - У адреса заказа нужны координаты: на шаге адреса — «Указать моё местоположение» (геолокация браузера) или выбор точки. Геокодер — только за интерфейсом с моком, ключи даёт владелец.
6. **Спор по ТЗ:** открывается любой стороной с PAID_HOLD по READY включительно. Открытый спор блокирует выплату. Решает админ; ИИ может только подсказывать (под флагом). Итоги спора: продолжить работу, полный возврат покупателю, частичный раздел — каждый оформляется транзакциями журнала. Таблицу переходов для спора опиши в ADR.
7. **Отмена:** покупателем до IN_PROGRESS — полный возврат («Деньги вернутся на вашу карту»); после — только через спор. Для этого нужны конечные статусы отмены и возврата — добавь их в таблицу переходов и ADR.
8. **Grade, KYC и реквизиты — по ТЗ и Handover:**
   - Grade: уровень, число завершённых заказов, `advancePercent` = 0, растёт после выплаты; аванс в интерфейсе не используется;
   - KYC мастера: статус PENDING | VERIFIED | REJECTED, загрузка удостоверения и регистрации ИП/ТОО через модуль `files`, проверка оператором;
   - реквизиты выплаты: IBAN с проверкой контрольной суммы KZ IBAN, хранится зашифрованным как ИИН.
9. **Путь до сделки — один, из ТЗ:** заявка → отклики и торг → оферта → оплата → работа → сдача → акт → выплата. Пять сценариев до договора, замерщик площадки и залог за выезд (ADR-005) — под флагом, по умолчанию выключены. Контрольный замер — Фаза 2.
10. **Контакты по ТЗ:** телефон и Instagram обеих сторон скрыты до заключения оферты (маскирование в чате работает до оферты). После оферты контакты видны обеим сторонам. Переключатель «имя исполнителя скрыто / показано» (ADR-006) остаётся. Согласие на показ телефона (ADR-008) после оферты не нужно — обнови ADR.
11. **Мастер заявки по ТЗ п. 3:** на первом шаге — только стиль и тип комнаты. Всё техническое (ЛДСП/МДФ, фурнитура, размеры, калькулятор материалов) — в свёрнутом блоке «Для продвинутых». До любой цели — 2–3 нажатия, нижняя навигация под палец. Текущий минималистичный стиль сохраняется; стиль Vercel-версии основателей (`escrowkz-web`) не использовать.

## 3. Платёжный контур и техника

### 3.1. Абстракция провайдера (ТЗ п. 10)

Интерфейс `PaymentProvider`: `hold`, `release`, `split`, `refund`, `getStatus`, `handleWebhook`. Каждая операция — с ключом идемпотентности; повтор не создаёт дубль. Провайдер выбирается конфигом; банк не вшит в бизнес-логику. Журнал транзакций (HOLD | RELEASE | SPLIT_MASTER | SPLIT_PLATFORM | REFUND, суммы в тиынах, ключ, внешний номер, документ-основание) — единственный источник правды о деньгах.

| Провайдер | Назначение | Что сделать |
|---|---|---|
| `mock` | Разработка и демо | Переделай текущий симулятор эскроу в мок под новый интерфейс; в интерфейсе честно помечен как тестовый |
| `manual` | **Мост к реальному банку** (Freedom Bank: эскроу без API, трёхсторонний договор, открытие и обслуживание 0 ₸, раскрытие по расписке) | Админ проставляет статусы денег кнопками: «Деньги поступили на счёт в банке», «Выплачено мастеру», «Доход платформы получен», «Возврат покупателю». Каждое действие — с номером и датой банковского документа и загрузкой скана; в аудит. Сгенерируй пакет для банка на раскрытие: акт с подписями + PDF-шаблон расписки (шаблон пометить «требует юридической проверки»). Пилот пойдёт на этом провайдере с реальными деньгами в банке |
| `freedompay` | Песочница: приём `POST /init_payment`, выплата `POST /api/reg2nonreg` | Реализуй строго по документации: подпись `pg_sig` (алгоритм — в Merchant API Overview), `pg_result_url`, payout notify, проверка подписи вебхуков, ретраи, защита от повторов. Карточные данные только на страницах провайдера. **Только окружение staging** |

**Старый режим `MANUAL`** (оплата напрямую мастеру по этапам) и оплаты этапов уходят из пути продукта. Удали их или спрячь за флагом, оформи миграцию и ADR.

**Ограничения Freedom Pay**, которые нужно отразить в `docs/OPEN_QUESTIONS.md` и `docs/bank/` (по публичной документации):
- двухстадийная оплата (`pg_auto_clearing=0`) держит сумму на карте около 5 дней (срок настраивается для мерчанта), после чего платёж автоматически подтверждается или отменяется. Для заказа длиной в недели холд не подходит;
- при одностадийной оплате деньги поступают мерчанту. Если мерчант — ТОО, это нарушает железное правило «деньги не проходят через счета ТОО».
Поэтому `freedompay` включается только в staging и не используется с реальными деньгами, пока Freedom Pay не подтвердит схему без зачисления на баланс ТОО. Код это гарантирует: в production провайдер `freedompay` запрещён проверкой окружения.

### 3.2. Окружения (ТЗ п. 11)

### 3.3. Уведомления

- iOS получает push только у установленного PWA (16.4+): покажи подсказку.
- Пуш и in-app уведомление — на каждое изменение денег и статуса заказа.

- Кнопка «Поделиться в WhatsApp» (`https://wa.me/?text=`) со ссылкой на документ: подписанная ссылка с ограниченным сроком, без персональных данных в тексте.

### 3.4. Остальное по ТЗ

- **Аудит:** кто, что, когда и **откуда** (IP с учётом `TRUST_PROXY`, user agent) — для каждого действия с деньгами и каждого перехода статуса.
- **Публичный read-only доступ к сделке (фундамент):** публичный идентификатор сделки, согласия обеих сторон, обезличенная проекция данных (без имён, телефонов, адреса, ИИН/IBAN), маршрут под флагом. Страница витрины — Фаза 2.
- **Название «Сенім» — в конфиге** `src/config/brand.ts` (имя, подпись, цвета): тексты, шаблоны PDF, манифест, сервис-воркер берут его оттуда. В `src/` не должно остаться захардкоженного имени — проверь тестом.
- **Документы ТЗ п. 7** в разделе «Документы» карточки: оферта (PDF), акт приёмки (PDF по макету стр. 18, с фото сдачи и GPS-отметкой), выписка по деньгам (PDF). Всё открывается с телефона, скачивается и пересылается.
- **Демо-данные** — честные тестовые сделки с пометкой «тестовые», никаких «полуфейковых». Пересобери сид под новую модель: сделки во всех статусах, со спором, с отменой, с выплатой.

## 4. Порядок работ и агенты

Используй агентов из `.claude/agents/`. Параллельные пишущие агенты — с `isolation: worktree`.

> **Важно про worktree:** изолированный worktree создаётся от основной ветки, а не от текущего HEAD. Поэтому сначала слей фундамент в локальную основную ветку или сделай основной веткой `feat/tz-v1`. Проверь, что агенты видят фундамент, прежде чем запускать фазу B.

**A — фундамент (ты сам, последовательно):**
1. ADR-009 (модель денег, статусы, провайдеры, флаги), обновление `CLAUDE.md`, `GLOSSARY.md`, `OPEN_QUESTIONS.md`.
2. Матрица соответствия `docs/TZ_COMPLIANCE.md`: каждый пункт ТЗ → файл/тест/экран → статус. Обновляй её в конце каждой фазы.
3. Модуль флагов и конфиг бренда.
4. Миграция схемы:
   - тиыны; статусы ТЗ;
   - журнал транзакций; раунды торга; оферта;
   - Grade; KYC; IBAN;
   - GPS-поля заказа и сдачи; координаты адреса;
   - IP и устройство в аудите;
   - публичный идентификатор и согласия; push-подписки;
   - собственноручные подписи.
5. Модуль расчёта денег с property-тестами. Интерфейс `PaymentProvider`. Коммит.

## 5. Банковские API эскроу — что положить в `docs/bank/06-bank-api-landscape.md`

Факты на 03.11.2026; что не подтверждено — так и помечено:
- **Freedom Bank:** продукт эскроу подтверждён банком (Handover): трёхсторонний договор, плательщик — физлицо, 0 ₸ открытие и обслуживание, раскрытие по расписке. **API нет** → провайдер `manual`.
- **Банк ЦентрКредит (БЦК):**
  - на портале `developer.bcc.kz` есть продукт **Escrow API 1.0.1** («сервис по работе со счетами эскроу»); операции публично не описаны, доступ — через кнопку «Получить доступ» на портале;
  - Handover: «Escrow API на рефакторинге»;
  - эскроу-счёт: открытие бесплатно, обслуживание 12 000 ₸/мес;
  - подключение к Open API: заявка или письмо на `oapi@bcc.kz` → менеджер в течение 1–3 рабочих дней → документы и тестовый доступ → заявление к типовому договору по API → тесты → прод; по словам банка, цикл обычно до месяца.
  - Провайдер `bcc` — только интерфейс и TODO до получения документации.
- **Alatau City Bank:** Business API, клиент написан в `escrowkz` (`bank-alatau.ts`), заблокирован на ключах и ЭЦП/NCALayer; публичной документации по эскроу не найдено.
- **Halyk, Kaspi:** публичных API эскроу не найдено (ePay и Kaspi Pay — приём платежей, не эскроу).
- **Типовой путь получения доступа** (пометить как типовой, уточнять у банка): расчётный счёт ТОО в банке → заявка на партнёрство → проверка компании и бенефициаров → договор по API → песочница → тестовые сценарии → прод; часто нужны ЭЦП юрлица для подписи запросов и белый список IP.
- **Вопросы к банку** (вынести списком): выписка и вебхуки по счёту сделки, частичное раскрытие и сплит (мастер + платформа), возврат, подтверждение раскрытия документом, сроки, тарифы, кто инициирует открытие счёта, может ли плательщик быть физлицом онлайн.
