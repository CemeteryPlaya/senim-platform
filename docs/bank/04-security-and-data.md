# 04. Безопасность и данные

Документ описывает, как платформа защищает вход, доступ к данным, персональные данные и журнал событий, и что нужно сделать до приёма реальных клиентов. Разделы 1–9 описывают реализованное и сверены с кодом; разделы 10–11 — план, исполнение которого за владельцем проекта.

## 1. Вход по SMS-коду

Код: `src/modules/identity/otp.ts`, лимиты — `src/platform/rate-limit.ts`.

- Код — 6 цифр, действует 5 минут, на один код — не больше 5 попыток ввода. Действует только последний выданный код.
- В базе хранится не код, а HMAC-SHA256 от номера и кода с ключом `PII_HASH_KEY`: по копии базы код не подобрать.
- Попытка засчитывается атомарно до сравнения, поэтому параллельный перебор не обходит лимит. Код гасится условным обновлением: два одновременных входа с одним кодом дают одну сессию.
- Лимиты считаются в Postgres (фиксированное окно, один атомарный `INSERT … ON CONFLICT` на попытку) и одинаково работают на нескольких инстансах.

| Лимит | Значение |
|---|---|
| Повторный код на номер | не чаще раза в минуту |
| Коды на номер | 5 в час, 10 в сутки |
| Проверки кода на номер | 20 в сутки (с любых IP) |
| Запросы кода с одного IP | 20 в час |
| Проверки кода с одного IP | 50 в час |
| Коды на новые номера (нет в базе) с одним префиксом (первые 6 цифр) | `OTP_DAILY_PREFIX_LIMIT`, по умолчанию 50 в сутки |
| Коды на все новые номера | `OTP_DAILY_GLOBAL_LIMIT`, по умолчанию 500 в сутки; при первом исчерпании за сутки — предупреждение в журнале и уведомление операторам |

Суточные потолки для новых номеров ограничивают расходы на SMS при рассылке по множеству номеров с множества адресов и не закрывают вход уже зарегистрированным пользователям.

**IP клиента** определяется только за доверенным прокси (`TRUST_PROXY=true`): берётся правый адрес `x-forwarded-for` (его дописал наш прокси), без него — `x-real-ip` (`src/app/_components/auth/client-info.ts`). Без доверенного прокси эти заголовки не читаются, лимиты по IP не применяются, остаются лимиты номера и суточные потолки. В `NODE_ENV=production` приложение не стартует без `TRUST_PROXY=true`.

Другие лимиты: указание ИИН заказчиком — 5 попыток в час (ответ «ИИН занят» раскрывает факт аккаунта, поэтому перебор ограничен), анкета исполнителя — 5 отправок в час.

**SMS-провайдер.** `SMS_PROVIDER=mock` — код в SMS никуда не уходит и показывается на экране только при `DEMO_MODE=true`; в лог пишутся только длина сообщения и последние 4 цифры номера. В production без демо-режима `mock` запрещён проверкой окружения. `SMS_PROVIDER=http` — общий каркас под казахстанский SMS-шлюз; формат запроса будет приведён к документации выбранного провайдера.

## 2. Сессии

Код: `src/modules/identity/session.ts`.

- Токен сессии — 32 случайных байта; в cookie `senim_session` с флагами `httpOnly`, `SameSite=Lax`, `Secure` в production, срок — 30 дней.
- В базе хранится SHA-256 токена, а не сам токен (таблица `Session`).
- Сессию можно отозвать: выход, «выйти на всех устройствах», блокировка пользователя. Сессия заблокированного пользователя недействительна. Новый вход в том же браузере отзывает прежнюю сессию.

## 3. Роли и проверка доступа

- **Каждый вход на сервер** (Server Action, route handler) разбирается zod-схемой (`action()` из `src/platform/action.ts`), первой строкой обработчика — `requireUser(...роли)`: нет сессии — «нужно войти», не та роль — «нет доступа».
- **Права над ресурсом** проверяет сервис модуля по данным из базы, а не по данным клиента. Типовые правила собраны в таблицу `POLICY` (`src/modules/identity/rbac.ts`): заказчик — только свои заявки и сделки, исполнитель — только свои отклики и сделки, оператор — все; действовать в сделке может только подтверждённый исполнитель.
- **Чужая запись — «не найдено».** Если пользователь не сторона сделки или заявки, сервис отвечает «не найдено» (`requireRole` в `deal-core/state.ts`, `requests/access.ts`), а не «нет доступа»: по ответу нельзя узнать, что запись существует. Попытки открыть чужие сделку и заявку и раздел оператора проверяются сквозными тестами (`e2e/09-access.spec.ts`), доступ к чужим файлам и PDF — интеграционными (`src/modules/files/access.int.test.ts`, `src/app/api/documents/[id]/pdf/route.int.test.ts`).
- **Действия в сделке** дополнительно проверяет таблица переходов: роль, текущий статус, условие (раздел «Статусные машины» в [02](02-architecture.md)).
- **Файлы** отдаются по подписанной ссылке (HMAC с `FILE_URL_SECRET`). Право доступа проверяется при выдаче ссылки; ссылка на фото сделки, споров, чата и документы живёт 15 минут, на портфолио и фото помещения — час. Загруженные файлы отдаются с `Content-Security-Policy: default-src 'none'; … sandbox`. Фото при загрузке пережимаются в JPEG без метаданных (EXIF с геолокацией и моделью телефона отбрасывается). Тип файла определяется по содержимому.
- **Документы** (PDF договора и актов) видят только стороны сделки и оператор; при выдаче PDF сервер сверяет SHA-256 файла с сохранённым.

## 4. Персональные данные

### ИИН/БИН

Код: `src/platform/crypto.ts`.

| Что хранится | Как | Зачем |
|---|---|---|
| `*IinEnc` | AES-256-GCM, случайный 12-байтовый IV, тег аутентичности; формат `v1.<iv>.<tag>.<шифртекст>`; ключ `PII_ENCRYPTION_KEY` (32 байта) | Расшифровывается только при формировании PDF договора |
| `*IinHash` | HMAC-SHA256 с отдельным ключом `PII_HASH_KEY` | Уникальность (один ИИН — один аккаунт заказчика, один профиль исполнителя на ИИН/БИН) и сверка ИИН сертификата ЭЦП без расшифровки |
| `*IinLast4` | последние 4 цифры | Показ в интерфейсе |

В интерфейсе ИИН/БИН показываются только последними 4 цифрами. Полностью они есть только в PDF договора. Ключи для разработки зашиты в код как производные от фиксированных строк; в `NODE_ENV=production` приложение не стартует без настоящих ключей.

### Анонимность исполнителя и маска контактов

- Заказчик видит исполнителя только как «Исполнитель №N» с сегментом, рейтингом, опытом и портфолио (`companies.publicExecutorView`). Наименование или ФИО и ИИН/БИН раскрываются только в договоре; телефон исполнителя не раскрывается нигде. Оператор видит телефон исполнителя последними 4 цифрами.
- Сообщения чата и тексты, которые видит другая сторона (отклик, отчёт по этапу, позиции в споре), проходят маску: телефоны (в том числе словами и с подменой символов), e-mail, ссылки и упоминания мессенджеров, наименование и ФИО исполнителя. Исходный текст не хранится; факт маскирования пишется в журнал (`chat.contacts_masked`), чтобы оператор видел повторяющиеся попытки. Маска — эвристика с известными ограничениями (`docs/OPEN_QUESTIONS.md`, № 20).
- Адрес заказчика раскрывается исполнителю только после выбора его отклика.

### Прочее

- ФИО и ИИН заказчика спрашиваются один раз перед договором (он сторона договора) и дальше не меняются — это защищает подписанные договоры.
- Перед отправкой текста ИИ-провайдеру ИИН/БИН, телефоны, e-mail, адреса и имена заменяются метками (`src/modules/ai/pii.ts`). ИИ-функции по умолчанию выключены.
- Телефон пользователя хранится открыто: это логин и адрес для SMS.
- Демо-данные — только тестовые: телефоны `+7 700 000 XX XX`, ИИН/БИН с верной контрольной суммой, но не принадлежащие людям.

## 5. Подпись договора и актов ЭЦП

Код: `src/modules/documents/service.ts`, `signature.ts`, `providers/`.

- Подписывается SHA-256 байтов PDF, сохранённый в `Document.sha256` при формировании. Сервер получает подпись (CMS) от провайдера и проверяет её сам: подпись действительна и подписан именно этот хэш. Подпись сохраняется только при совпадении хэша, под блокировкой строки документа.
- **Подписант привязан к стороне сделки.** ИИН из сертификата сверяется **целиком**: его HMAC сравнивается с хранимым HMAC ИИН подписанта стороны (заказчик — его ИИН; ТОО — ИИН директора из профиля; ИП и самозанятый — ИИН владельца). Подпись чужим сертификатом отклоняется. Последние 4 цифры ИИН сертификата хранятся только для показа.
- Подписанный договор не перевыпускается. Неподписанный при отмене сделки снимается с подписи (`SUPERSEDED`).
- **Провайдеры.** `SIGNATURE_PROVIDER=mock` — подпись имитируется, в интерфейсе предупреждение «Демо-режим: подпись имитируется и не имеет юридической силы»; в production без демо-режима `mock` запрещён. `SIGNATURE_PROVIDER=sigex` — порт `SigexClient` (начать QR-подписание в eGov Mobile, получить CMS, проверить CMS и получить ИИН сертификата) и логика вокруг него готовы и проверены тестом с поддельным клиентом; HTTP-клиент SIGEX пишется по документации SIGEX после получения доступа. Пока клиента нет, подпись через SIGEX отвечает «ещё не подключена». NCALayer подключается вместе с передачей CMS с клиента.
- БИН организации в сертификате ТОО провайдер подписи пока не возвращает: сверка БИН — после подключения SIGEX.

## 6. Журнал аудита

Код: `src/modules/audit/index.ts`, триггер — `prisma/migrations/20261030144535_init/migration.sql`.

- Каждое изменение состояния (сделка, этап, оплата, документ, спор, денежная операция, решения оператора, переключение режима оплаты) пишется в `AuditEvent` **в той же транзакции**, что и само изменение: нет изменения без записи и записи без изменения.
- Запись: кто (пользователь и роль или система), действие (`deal.stage.accepted`), сущность, состояние до и после, дополнительные поля, время и сквозной номер `seq`. `scope` («`deal:<id>`») собирает всю историю сделки с этапами и платежами одним запросом.
- **Только добавление.** Сервис не умеет изменять и удалять записи, а база запрещает это триггером:

  ```sql
  CREATE TRIGGER audit_event_no_update_delete
    BEFORE UPDATE OR DELETE ON "AuditEvent"
    FOR EACH ROW EXECUTE FUNCTION audit_event_append_only();
  ```

  Любой `UPDATE` или `DELETE` по журналу, в том числе прямым SQL через подключение приложения, завершается ошибкой.
- **Ограничение.** Триггер срабатывает на `UPDATE`/`DELETE`, но не на `TRUNCATE`. `TRUNCATE` использует только «Сбросить демо» (`src/demo/seed.ts`), доступный при `DEMO_MODE=true`. В рабочем окружении приложение должно подключаться к базе ролью без права `TRUNCATE` и без владения таблицами; миграции — отдельной ролью. Это часть плана развёртывания (раздел 10).
- Оператор просматривает журнал с фильтрами (`/operator/audit`); страница показа банку выводит историю выбранной сделки.

## 7. Заголовки и периметр

Заголовки для всех ответов (`next.config.ts`):

| Заголовок | Значение |
|---|---|
| `X-Frame-Options` | `DENY` |
| `Content-Security-Policy` | `frame-ancestors 'none'` (для `/api/files/*` — свой, строже) |
| `Referrer-Policy` | `no-referrer` |
| `X-Content-Type-Options` | `nosniff` |
| `Permissions-Policy` | камера — только свой сайт (фото этапов с телефона); микрофон, геолокация, платежи, USB — запрещены |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains` (только в production) |

Заголовок `X-Powered-By` отключён. Полный CSP для скриптов не задан, чтобы не сломать встроенные скрипты Next.js; это направление доработки.

Тело вебхука ограничено 64 КБ, тело Server Action — 4 МБ (фото этапов). Cron-маршрут закрыт секретом `CRON_SECRET` (сравнение за постоянное время); в production без него маршрут не выполняет задачи.

## 8. Демо-стенд

Демо-режим (`DEMO_MODE=true`) включает демо-персоны (вход одним нажатием), «Сбросить демо», страницу показа банку `/bank-demo` и переключатель режима оплаты. В рабочем окружении с реальными клиентами — только `false`.

- Вход персоной проверяет на сервере и флаг `DEMO_MODE`, и признак `isDemo` пользователя; сессия создаётся обычным путём. (В старом MVP можно было войти под любым пользователем, подставив его id в cookie; это исправлено.)
- В production при `DEMO_MODE=true` весь сайт закрыт паролем показа `DEMO_ACCESS_PASSWORD` (HTTP Basic, не короче 16 символов, сравнение за постоянное время; `src/proxy.ts`, `src/platform/demo-gate.ts`). Без пароля доступны только точные пути `/api/webhooks/bank`, `/api/webhooks/escrow-simulator` и `/api/cron/run`, у которых своя проверка подписи или секрета. При пароле обязателен и `CRON_SECRET`.
- Секрет подписи вебхуков симулятора в production обязателен (`ESCROW_SIMULATOR_WEBHOOK_SECRET`); локально без него используется случайный секрет процесса.

## 9. Логи

Код: `src/platform/logger.ts`. Вывод в консоль разрешён только здесь; остальной код пишет через `logger`.

- Строки JSON с временем, уровнем и полями.
- Значение поля не пишется, если в имени поля есть `iin`, `bin`, `phone`, `code`, `otp`, `token`, `password`, `secret`, `authorization`, `cookie`, `signature`, `text`, `body`, `fullname`, `address`, `legalname`, `comment`, `report`, `description`, `position`.
- В текстах ошибок 12 цифр подряд (ИИН/БИН) и телефоны заменяются на «[скрыто]». Ошибки Prisma пишутся без сообщения (в нём аргументы запроса) — только имя, код и стек.
- Те же правила — для текста ошибки фоновой задачи, который хранится в базе и виден оператору.

## 10. Хранение данных в РК при запуске

**Требование.** Персональные данные граждан РК должны храниться в базе на территории Казахстана (Закон РК «О персональных данных и их защите»). Поэтому:

- **Сейчас** демо и показ банку — на Vercel, только с тестовыми данными. Реальных клиентов на этом окружении нет.
- **До приёма реальных клиентов** приложение переезжает в облако в РК. Выбор провайдера, договор и настройка — задача владельца проекта (`docs/OWNER_TODO.md`, п. 11).

Код готов к переезду без переписывания: различаются только переменные окружения.

| Компонент | Демо (Vercel) | Рабочее окружение в РК (план) |
|---|---|---|
| Приложение | Vercel Functions | Node.js 22 в облаке РК: `npm ci`, `prisma migrate deploy`, `npm run build`, `npm start` (за обратным прокси с TLS, `TRUST_PROXY=true`) |
| База | Postgres провайдера Vercel Marketplace | Управляемый PostgreSQL в РК; отдельные роли для приложения (без `TRUNCATE` и владения таблицами) и для миграций; шифрование диска; доступ только из сети приложения |
| Файлы | Vercel Blob (приватное хранилище) | S3-совместимое хранилище в РК: `STORAGE_PROVIDER=s3`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, ключи доступа; приватный бакет, доступ по подписанным ссылкам |
| Фоновые задачи | Vercel Cron, раз в сутки | Планировщик облака вызывает `GET /api/cron/run` с `Authorization: Bearer <CRON_SECRET>` не реже раза в 15 минут |
| Секреты | Переменные Vercel | Хранилище секретов облака; `PII_ENCRYPTION_KEY` и `PII_HASH_KEY` — отдельно от резервных копий базы |
| Режим | `DEMO_MODE=true`, пароль показа | `DEMO_MODE=false`; `SMS_PROVIDER=http` и `SIGNATURE_PROVIDER=sigex` (моки в production без демо запрещены) |

## 11. Резервные копии (план)

Резервное копирование обеспечивает облачный провайдер; в коде его нет. Предлагаемый порядок, который владелец согласует с провайдером:

1. **База:** ежедневная полная копия и непрерывный архив журнала транзакций (восстановление на момент времени); хранение копий — в РК, в зашифрованном виде; срок хранения определяется вместе с юристом.
2. **Файлы:** версионирование бакета S3 и защита от удаления на срок хранения; PDF договоров и актов не изменяются после создания (их хэш подписан).
3. **Ключи:** `PII_ENCRYPTION_KEY` и `PII_HASH_KEY` хранятся отдельно от копий базы и сами резервируются: без ключа шифрования ИИН/БИН из копии не восстановить, без ключа HMAC перестают работать поиск и сверка ИИН.
4. **Проверка восстановления:** регулярное восстановление копии на отдельный стенд с проверкой журнала аудита (непрерывность `seq`) и сверкой операций по сделкам.
5. Журнал аудита входит в копию базы; восстановление не нарушает его неизменяемость (триггер восстанавливается вместе со схемой).
