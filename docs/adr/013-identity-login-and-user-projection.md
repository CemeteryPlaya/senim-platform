# ADR-013: Вход через identity и проекция пользователя в web

Статус: принято (план 2, 10.11.2026; решения контроллера в ходе плана).

## Контекст

В плане 2 вход, сессии и роли переехали из `apps/web` (Prisma, таблицы `Session`, `OtpCode`) в Go-сервис `identity`. Старая база `web` при этом остаётся: в ней живут заявки, сделки, профиль, ИИН/БИН и IBAN, и ссылаются они на `User.id`. Схема Prisma не меняется (меньше конфликтов `git subtree pull`), таблицы `Session` и `OtpCode` перестают использоваться и удаляются в плане 7. Нужно было решить, кто генерирует токен сессии, как не разойтись двум хранилищам пользователя и в каком порядке выдавать роль исполнителя.

## Решение

1. **Токен сессии генерирует `web`**, передаёт его в `VerifyOtp` / `StartDemoSession`, `identity` хранит только sha256. Причина — идемпотентность: повтор `VerifyOtp` с тем же `idempotency_key` после обрыва связи должен вернуть тот же ответ. Если бы токен выдавал `identity`, его пришлось бы сохранить вместе с ответом (секрет в таблице идемпотентности) или выдать другой (вторая сессия). С токеном от `web` ответ секрета не содержит: повтор опознаётся по ключу и тому же токену, сессия одна. Токен в `identity` и в логи не попадает — только хеш.
2. **Старая таблица `User` — проекция пользователя `identity`.** Тот же `id` (идентификатор выдаёт `identity`). `web` создаёт и обновляет строку из ответов `identity` (`VerifyOtp`, `Authenticate`, `SwitchRole`, `GrantRole`), поля профиля (ФИО, ИИН, IBAN, KYC) остаются только в старой базе. Конфликт: строка с тем же телефоном, но другим `id` — ошибка с записью в лог, а не второй пользователь и не молчаливая замена `id`.
3. **Регистрация исполнителя: сначала роль, потом профиль.** `web` вызывает `GrantRole` (случайный `idempotency_key` — выдача роли сама по смыслу идемпотентна: «уже выдана» даёт `granted=false` без события; фиксированный ключ при другой сессии давал бы `idempotency_key_reused`), затем выполняет прежнюю транзакцию старой базы. Сбой между шагами оставляет роль без профиля, а не профиль без роли; повтор формы доводит дело до конца.
4. **Прежняя сессия браузера отзывается после успешного `VerifyOtp`**, не до. Неверный код не выбрасывает человека из действующей сессии (как в старом web).
5. **Идентификация вызывающего и права** — как в ADR-011: все методы только для `web`, `GetSigningKeys` — для любого сервиса из `tools/services`. Внутренний токен — JWT EdDSA, 5 минут, `kid`; проверка — `pkg/authz` по ключам из `GetSigningKeys`.
6. **Ротация ключа подписи:** сначала публиковать новый публичный ключ (`IDENTITY_TOKEN_PREVIOUS_PUBLIC_KEY` — прежний публичный ключ на время ротации), и только после того, как все проверяющие его получили, начинать подписывать им. Иначе проверяющий увидит неизвестный `kid`.

## Вынесено

- **План 2б (до плана 3):** ПДн в `identity` (ФИО, ИИН/БИН, IBAN с envelope-шифрованием и `kid`, HMAC-поиск), KYC, согласия, 2FA операторов (TOTP/WebAuthn) и повторная 2FA для денежных действий.
- **План 6 (`notify`):** доставка кода через Telegram Gateway / SMS (в плане 2 только мок, поэтому `APP_ENV=prod` вход не запускает), уведомление операторам при исчерпании суточного потолка кодов (событие `OtpGlobalLimitReached` пишется в outbox, получателя нет), потребитель аудита (события `identity` пока никто не читает).
- **План 7:** удаление `Session` и `OtpCode` из Prisma. Блокировка пользователя в `identity` пока не доходит до `User.blockedAt` старой базы — нужен путь событий, план не назначен.

## Цена ошибки каждого решения

| Решение | Если ошибочно |
|---|---|
| Токен от `web` | Утечка из логов `web` — угон сессии; смена на токен от `identity` потребует хранить секрет в ответе идемпотентности и менять контракт `VerifyOtp`. |
| Проекция `User` | Расхождение `id` или блокировки между базами: заблокированный в `identity` остаётся «живым» в старой базе до плана событий (известно, в отложенном). Откат — вернуть чтение `Session` из старой базы: данные там не удалялись. |
| Роль, потом профиль | Роль без профиля: человек видит экран регистрации ещё раз, повтор безвреден. Обратный порядок дал бы профиль без права и осиротевшие данные. |
| Отзыв старой сессии после входа | Короткое окно, когда у браузера две живые сессии; закрывается 30-минутным простоем. |
| Мок доставки кода до плана 6 | Без `notify` прод-вход невозможен — это намеренно (проверка конфига при старте), цена — пилот ждёт план 6. |

## Последствия

- Плюс: повтор после обрыва не создаёт второй сессии и не даёт «код устарел»; `web` и `identity` не делят секретов, кроме того, что токен виден самому браузеру.
- Минус: до плана 2б два хранилища пользователя; согласованность держится на коде `web`, а не на транзакции.
- Минус: `web` не отличает «identity лежит» от «web сломан» в оболочке (оба дают `UNAVAILABLE`); отложено.
