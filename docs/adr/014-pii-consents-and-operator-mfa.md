# ADR-014: ПДн, согласия и 2FA операторов в identity

Статус: принято (план 2б, 11.11.2026; решения контроллера в ходе плана — таблица «Решения» раздела «План 2б» в `docs/PROGRESS.md`).

## Контекст

После плана 2 (ADR-013) ФИО, ИИН/БИН, IBAN и KYC жили в старой базе `web`, зашифрованные ключом самого `web`, а операторы входили одним кодом из SMS. Спека (§4.1, §4.4, §5, §8) отдаёт ПДн, KYC, согласия и вторую ступень входа сервису `identity`; правовая основа — `docs/legal/2026-11-07-legal-research.md` (A.2 — согласие и отзыв, A.7, A.8 — структура текста). Нужно было решить, как хранить и раскрывать ПДн, как не разойтись со старой базой, чем подтверждать согласие, как исполнять отзыв и как устроить 2FA, пока денежные действия ещё в `web`.

## Решение

1. **Шифртекст.** Конвертное шифрование `pkg/pii`: у каждого значения свой ключ данных, AES-256-GCM и для значения, и для обёртки ключа данных ключом шифрования ключей (KEK). Формат: `v2.<kid>.<base64url(обёрнутый ключ данных)>.<base64url(nonce‖шифртекст‖tag)>`. AAD — `identity.<таблица>.<поле>:<user_id>`, пустой AAD отклоняется: шифртекст, перенесённый в чужую строку, не расшифровывается. Шифруются ИИН человека, БИН/ИИН исполнителя, ИИН подписанта, IBAN и секрет TOTP; ФИО, Instagram, e-mail и телефон — открыто. Рядом хранятся последние 4 символа для показа и слепой индекс HMAC-SHA256 (домены `iin`, `bin_iin`) с уникальностью: один ИИН — один человек, один БИН/ИИН — одна сторона; гонка двух регистраций даёт `iin_taken`, а не `Internal`. ИИН подписанта индексируется без уникальности (один директор у нескольких ТОО) — для сверки с ЭЦП (`VerifySignerIin` со стороной подписи, без раскрытия).
2. **Ключи и перешифровка.** KEK — из переменных `PII_KEKS` (`kid:base64,…`, ровно 32 байта) и `PII_KEK_CURRENT`, ключ индекса — `PII_INDEX_KEY` (на стенде — `IDENTITY_PII_*` в `deploy/compose/dev.vars`); вне dev все ключи разные и отличаются от прочих секретов сервиса. KMS — позже интерфейсом (облако РК не выбрано), формат и AAD при этом не меняются. Новые значения шифруются текущим `kid`, прежние читаются, пока их `kid` есть в конфиге. `identity rewrap-pii [--batch 500]` перешифровывает только ключи данных на текущий `kid` пачками по транзакции: повреждённое значение пропускает и выходит с кодом 1, неизвестный `kid` — останавливается. При старте `serve` сверяет все `kid` в `persons`, `parties`, `mfa_factors` с конфигом: ключ убран раньше перешифровки — сервис не стартует и называет `kid`.
3. **Раскрытие и аудит чтения.** Открытые ИИН/БИН/IBAN выдаёт только `RevealPartyDetails{purpose, reference_id}` (цели `CONTRACT`, `RELEASE_RECEIPT`, `PAYOUT`; до 50 субъектов). На каждого субъекта — событие аудита `pii.revealed` в outbox с целью, ссылкой и именами полей, без значений. Сессия действующего лица необязательна: без неё (фоновые оплата и выплата, сид, подпись) действующее лицо — сервис `web`; операторская сессия требует пройденной 2FA. Участие в сделке проверяет `web` до вызова. Выдача ссылок на файлы KYC — событие `pii.kyc_file_link_issued` в журнале `web`.
4. **Проекция в старую базу.** `web` больше не шифрует и не хранит ИИН/БИН/IBAN: пишет через gRPC, а в `User` (`fullName`, `iinLast4`, `instagram`, `email`) и `ExecutorProfile` (форма, название, последние 4 символа, статус KYC) переносит ответ `identity` (`projectPerson`, `projectParty`); экраны с последними 4 символами не меняются. Столбцы `*Enc`/`*Hash` в Prisma перестают заполняться, удаляются в плане 7. Данные не переносятся: v2 стартует с чистой базой и демо-сидом. Файлы KYC остаются в `web` (`StoredFile`, UUID), `identity` хранит их `id`. `UpdateContacts` задаёт полное новое состояние контактов (пустая строка очищает).
5. **Согласие подтверждается сессией входа.** Экран согласия идёт сразу после входа; запись — версия, SHA-256 показанного текста, цели, канал и `session_id` сессии. Канал — по тому, как открыта сессия (`sessions.opened_by`, миграция 0010): `otp_session` — входом по коду из SMS, `demo` — демо-входом без кода (`StartDemoSession`, только `DEMO_MODE`), `seed` — сид без сессии. Запись не меняется и не удаляется (триггер; у рабочей роли нет `DELETE`), можно лишь один раз отметить отзыв; новая редакция — новая запись. В действие передаётся версия показанного текста: не совпала с текущей — `CONFLICT`, экран просит прочитать новую. Без согласия текущей версии `web` пускает только на экран согласия и выход. Сотрудники (`OPERATOR`, `MEASURER`) экран не проходят — их данные обрабатываются по трудовому договору. Согласие на передачу банку (`BANK_TRANSFER`, P3) — отдельное, на сделку: исполнитель даёт его при подписании оферты, покупатель — на шаге оплаты. Подпись оферты без отметки закрыта только в интерфейсе (сервер оферту без неё не отклоняет); деньги защищает оплата: `payForDeal` без согласий обеих сторон отклоняется на сервере. Демо-сделки получают его через `SeedConsents` (только `DEMO_MODE`, вызывающий `web`, канал `seed`). Тексты — черновики в `apps/web/src/i18n/ru/consent.ts` (первая строка «Черновик, требует юридической проверки», редакция `2026-11-11-d1`).
6. **Отзыв согласия на ПДн — заявка.** `RevokeConsent` создаёт заявку `REQUESTED` со сроком 15 рабочих дней (пн–пт по `Asia/Almaty`; праздники РК не учитываются — срок выходит не позже законного). Согласие остаётся действующим до решения оператора: `COMPLETED` отзывает согласия, данные до заявки; `REFUSED` (причина 3–500 символов) оставляет согласие. Пока заявка открыта, повторное согласие той же версии возвращает прежнюю запись, а экран новой редакции не показывается. Само удаление и блокировка данных по всем сервисам — до пилота, когда появятся `deal` и `marketplace`; до тех пор оператор исполняет отзыв по регламенту вручную и отмечает итог в очереди.
7. **TOTP и первое подключение.** Вторая ступень — только TOTP (RFC 6238: HMAC-SHA1, 30 с, 6 цифр, ±1 шаг), только для роли `OPERATOR`; WebAuthn — позже за флагом. Секрет 20 байт шифруется `pkg/pii` (AAD `identity.mfa_factors.secret:<user_id>`); принятый шаг запоминается — тот же код второй раз даёт `mfa_code_reused`; неверных кодов не больше 5 за 15 минут, верный код попытку возвращает. Первое подключение — по сессии, открытой кодом входа (доверие при первом использовании), с событием `MfaEnrolled` и аудитом. Сброс — подкоманда владельца `identity mfa-reset --phone …`: удаляет фактор, снимает отметку со всех сессий, пишет `MfaReset` и аудит (`actor_kind = cli`). Операторские методы `identity` (`ProvisionExecutor`, `ListKycQueue`, `ReviewKyc`, `ListConsentRevocations`, `ResolveConsentRevocation`, `RevealPartyDetails` с сессией оператора) без `mfa_verified_at` отвечают `mfa_required`. В `web` без пройденной 2FA оператор открывает только `/operator/mfa`, `/profile`, `/switch-role` и `/consent` (чужих ПДн там нет); все остальные страницы и все действия — отказ.
8. **Повторная 2FA для денег.** Денежное действие оператора требует код TOTP, введённый не раньше 5 минут назад (`MFA_STEP_UP_WINDOW`, по умолчанию `5m`, допустимо 1–30 мин). До плана 3 деньги в `web`, и окно проверяет `web` (`requireRecentMfa` в действиях `/operator/money` и `/operator/disputes`); `identity` окно не применяет, только отдаёт в сессии `mfa_verified_at`, а во внутреннем токене — `mfa` и `mfa_at`. С плана 3 проверяет `deal` через `authz.RequireRecentMFA` по токену. Демо: при `DEMO_MODE` демо-сессия оператора считается прошедшей 2FA, повторный код не спрашивается (у демо-персон нет приложения); `APP_ENV=prod` запрещает `DEMO_MODE`.

## Вынесено

- **До пилота:** исполнение отзыва по всем сервисам (удаление, блокировка, сроки хранения по обязательствам `deal` и `marketplace`); производственный календарь РК для срока отзыва; уведомление человеку о решении по отзыву.
- **Юрист и владелец:** тексты согласий, канал подтверждения (`otp_session` или код на само согласие), казахский язык (P18), перечень ПДн (P5), ответственное лицо (P12), нужно ли согласие сотрудников.
- **План 3** (до первого денежного действия в `deal`, решение контроллера по финальному ревью):
  - повторная 2FA в `deal` (`authz.RequireRecentMFA`), переменная `MFA_STEP_UP_WINDOW` в конфиге `deal`. Демо-исключение сейчас есть только в `web` (`requireRecentMfa`, `apps/web/src/modules/identity/mfa.ts`), у `authz.RequireRecentMFA` его нет — демо-оператор упрётся в отказ `deal`. Варианты: (а) `identity` при `DEMO_MODE` и демо-сессии оператора выдаёт внутренний токен с `mfa_at = now` — `deal` исключений не знает, демо-ветка живёт там же, где запрет `DEMO_MODE` в prod; (б) флаг демо в конфиге `deal`, запрещённый при `APP_ENV=prod`, — проще, но исключение во втором сервисе. Плюс политика кэша внутреннего токена в `web` после `VerifySecondFactor` и `mfa-reset`: сейчас токен берётся на каждый запрос; спека допускает кэш до 5 минут — тогда после ввода кода кэш сбрасывается, иначе `deal` увидит старый `mfa_at`, а после `mfa-reset` токен с `mfa=true` живёт до конца кэша;
  - раскрытие по цели — таблица «цель → поля» в `reveal.go` (минимизация, A.7): сейчас `RevealPartyDetails` отдаёт все реквизиты при любой цели; `PAYOUT` — только IBAN и наименование получателя, подпись — только то, что нужно сверке, `CONTRACT` — реквизиты сторон договора. Тест на каждую пару цель/поле;
  - получатель выплаты фиксируется в `deal` при создании `SPLIT_MASTER` (IBAN и наименование — в записи журнала денег), блокировка смены IBAN проверяется в транзакции `deal`: сейчас `payout-lock` в `web` не атомарна с `SetPayoutIban` в `identity` — смена счёта между проверкой и выплатой уведёт деньги на новый счёт. Варианты: снимок реквизитов в `deal` (выплата идёт по снимку, смена IBAN после — на эту выплату не влияет) или запрет `SetPayoutIban` в `identity` по событию «выплата начата» от `deal` (нужен обратный поток событий).
- **План 4:** файлы KYC — сервис `files`.
- **План 6:** потребитель аудита (`pii.revealed` и прочие события `identity` пока никто не читает); уведомление мастеру о решении KYC по событию `KycReviewed`.
- **План 7:** KMS вместо KEK в переменной; удаление `*Enc`/`*Hash` из Prisma; перенос ключа мок-подписи с `PII_ENCRYPTION_KEY` `web`.

## Цена ошибки каждого решения

| Решение | Если ошибочно |
|---|---|
| Конверт и AAD с `user_id` | Ошибка в AAD делает значения нечитаемыми, а не чужими; перенос значения между пользователями оператором невозможен без расшифровки и записи заново. |
| KEK в переменной, KMS позже | Утечка переменной и копии базы раскрывает все ПДн; смена ключа — `rewrap-pii`, перешифровка самих значений не нужна. Во время перешифровки секрета TOTP возможен один отказ проверки кода. |
| Слепой индекс с уникальностью | Утечка ключа индекса позволяет перебором проверить, есть ли ИИН в базе (12 цифр с контрольной суммой). Лимит перебора — 5 попыток в час: ИИН человека считает `identity`, БИН/ИИН исполнителя — `web`; при компрометации `web` перебор БИН/ИИН без лимита. |
| Раскрытие от имени сервиса без сессии | В аудите при подписи и фоновых операциях действующее лицо — `web`, а не человек; ошибка проверки участия в `web` раскрывает чужие ПДн (identity доверяет `web` по mTLS). |
| Проекция в `User` и `ExecutorProfile` | Расхождение последних 4 символов или статуса KYC между базами до плана 7; источник правды — `identity`, повторная запись чинит проекцию. Забытое поле в `UpdateContacts` стирает контакт. |
| Согласие сессией входа (`otp_session`) | Юрист может потребовать отдельный код на само согласие (A.2 «надёжнее»): новый RPC подтверждения и экран, записи прежних согласий останутся с каналом `otp_session`. |
| Сотрудники без согласия | Если юрист потребует согласие и от сотрудников — экран согласия для `OPERATOR`/`MEASURER` и тексты для них. |
| Отметка банку при оферте — только в интерфейсе | Прямой вызов подписи оферты без отметки пройдёт; сделку без согласий обеих сторон всё равно не оплатить (проверка в `payForDeal`). |
| Отзыв — заявка, согласие действует до решения | До решения оператора человек пользуется платформой по действующему согласию (и прежней редакции); передумавший ждёт решения. Ручное исполнение до пилота — риск пропустить срок или сервис; праздники не учтены (срок раньше законного, не позже). |
| Только TOTP, первое подключение по SMS | Кто перехватил SMS оператора до первого подключения, подключит свой TOTP; потеря телефона — только `mfa-reset` у владельца. Внутренние токены с `mfa=true` живут до 5 минут после `mfa-reset` (срок токена; сессия отметку теряет сразу). Повтор `StartTotpEnrollment` после истечения сессии даёт `session_invalid`, а не сохранённый ответ (сессия проверяется раньше идемпотентности); после подтверждения — `mfa_already_enrolled`. |
| Окно 5 минут в `web`, потом в `deal` | Два денежных действия в пределах 5 минут — один ввод кода; значение задано в двух местах (`web` сейчас, `deal` в плане 3). Граница окна в браузере не проверяется (только в vitest). |
| Демо без 2FA | На демо-стенде повторная 2FA не показывается; после «Сбросить демо» операторы заново подключают TOTP. Защита — запрет `DEMO_MODE` в prod. Исключение — только в `web`: до решения в плане 3 (вынесено выше) денежное действие демо-оператора в `deal` получит отказ. |
| Канал согласия по способу открытия сессии | Сессии, открытые до 0010, помечены по признаку демо пользователя: прежняя сессия демо-пользователя, вошедшего кодом, даёт канал `demo` (слабее, а не сильнее правды). |

## Последствия

- Плюс: открытые ИИН/БИН/IBAN есть только в памяти `identity` и в ответе `RevealPartyDetails`, каждое раскрытие оставляет событие; `web` не держит ключей ПДн, кроме ключа мок-подписи.
- Плюс: оператор без TOTP не меняет чужие данные и не видит чужие ПДн ни через экраны, ни прямым вызовом.
- Минус: каждый экран с ПДн и каждое раскрытие — вызов `identity`; при его недоступности договор, подпись и выплата не идут.
- Минус: исполнение отзыва и тексты согласий не готовы к пилоту без юриста и без `deal`/`marketplace`.
