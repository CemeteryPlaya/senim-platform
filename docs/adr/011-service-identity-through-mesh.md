# ADR-011: Удостоверение сервиса через mesh

Статус: принято (финальная волна исправлений плана 1, 08.11.2026; решение контроллера по замечанию I1 финального ревью).

## Контекст

Спека (§4.4): «Сервис ↔ сервис: mTLS с удостоверением сервиса»; анти-цель — «сервис доверяет вызывающему без проверки прав». План 1 построил путь `web → mesh (Envoy) → сервис`, где:

- mesh завершал mTLS вызывающего, вычищал `x-forwarded-client-cert` (`SANITIZE`) и шёл к сервису со своим сертификатом `mesh`. Сервис видел `mesh` у каждого вызова — отличить `web` от `operator` было нельзя, и запланированный «список CN» в сервисе мог бы разрешить или запретить только `mesh`;
- `pkg/tlsx.ServerConfig` принимал любой сертификат нашего CA: владелец любого сертификата (web, а также edge, которому devcerts выдавал сертификат без надобности) мог позвонить в порт сервиса напрямую в обход списка SAN в mesh.

План 2 добавляет первые настоящие RPC (выдача внутреннего токена — её может звать только `web`), а планы 3–6 копируют выбранный шаблон.

## Решение

Вариант (a) ревью: удостоверение вызывающего несёт mesh в XFCC, сервис доверяет XFCC только от mesh.

1. **mesh** (`deploy/compose/envoy/mesh.yaml`): `forward_client_cert_details: SANITIZE_SET` и `set_current_client_cert_details: {uri: true, dns: true}`. Envoy отбрасывает любой входящий XFCC и пишет одно звено — текущее: DNS SAN (и URI) клиентского сертификата, который он проверил по списку SAN (`web` и Go-сервисы).
2. **Сервис принимает соединение только от разрешённых сертификатов**: `server.Options.AllowedPeers` (обязательно) → `tlsx.ServerConfig(..., allowedPeers)`. После проверки цепочки `VerifyConnection` требует, чтобы у листа был ровно один DNS SAN кроме `localhost` (он есть в каждом dev-сертификате и удостоверением не считается) и чтобы это имя было в списке (`tlsx.PeerName`). Сертификат без имени или с двумя именами (например `web` и `mesh`) отвергается: он не может пройти как более привилегированный. Любой другой сертификат того же CA — отказ на рукопожатии. Шаблон сервиса: `AllowedPeers = [server.MeshPeer, <сам сервис>]` — mesh и собственные реплики/подкоманды. identity так и настроен.
3. **`server.Caller(ctx)`** — кто вызвал (интерсептор `pkg/server`, до логирования):
   - TLS-пир — `mesh`: вызывающий из XFCC. Разбор строгий: ровно одно значение заголовка и одно звено (запятая вне кавычек — ошибка), только известные ключи Envoy (`By`, `Hash`, `Cert`, `Chain`, `Subject`, `URI`, `DNS`), кавычки и `\"` внутри них, единственное DNS-значение кроме `localhost` (два — ошибка, как в `tlsx.PeerName`), и оно должно быть именем сервиса. Нет XFCC — вызывает сам mesh (активная проверка здоровья Envoy). Неразборчивый XFCC от mesh — `PermissionDenied` и запись в лог, а не догадка.
   - Любой другой допущенный TLS-пир (прямой вызов своей реплики) — его DNS SAN; XFCC от него игнорируется (подделка ничего не даёт).
   - Имя вызывающего возвращается в заголовке ответа `x-senim-caller` (дымовой тест видит, что удостоверение пережило mesh; вызывающий узнаёт только своё имя) и пишется в лог RPC (`caller`).
4. **edge не получает сертификат внутреннего CA** (`tools/services.Certs`): он говорит с web по HTTP внутри сети стенда и не звонит ни в mesh, ни в сервисы.
5. Это решение заменяет пункт журнала «CN allow-list interceptor в плане 3»: удостоверение готово сейчас. **Таблица прав «какой вызывающий может звать какой метод» остаётся за планом 3** (первые методы, двигающие деньги), а для выдачи токена в плане 2 — проверка `Caller(ctx) == "web"` в обработчике.

## Проверка

- `pkg/tlsx`: допущенный пир принят, сертификат того же CA с другим SAN отвергнут на рукопожатии, `localhost` не удостоверение, сертификат с двумя именами отвергнут, пустой список — ошибка.
- `pkg/server`: прямой вызов — имя по SAN; через mesh — по XFCC (в том числе кавычки и `Subject` с запятой); подделанный XFCC от не-mesh игнорируется; 10 вариантов битого XFCC от mesh — `PermissionDenied`; без `AllowedPeers` `Run` не стартует.
- `services/identity`: сертификаты `web` и `deal` напрямую отвергнуты, `mesh` и `identity` приняты.
- Живой стенд (`test/smoke`): через настоящий Envoy identity видит вызывающего `web`, подделанный клиентом XFCC вычищен; изнутри контейнера web прямой звонок в `identity:8443` с сертификатом web — алерт `bad certificate`, а в `mesh:9443` с ним же — принят; сертификат нашего CA с SAN `edge` mesh отвергает.

## Последствия

- Плюс: каждый сервис знает, кто его вызвал, и прямой обход mesh закрыт на уровне TLS — до появления первого RPC с правами.
- Плюс: один шаблон для всех сервисов плана 2 (`AllowedPeers` + `Caller`), без сетевой сегментации как единственной защиты.
- Минус: доверие XFCC держится на секретности ключа `mesh`; ключ mesh — самый ценный из сервисных. В Kubernetes (план 7) добавить NetworkPolicy (к портам сервисов — только mesh) как вторую линию.
- Минус: если сервису однажды понадобится звать другой сервис напрямую (не через mesh), его имя придётся добавить в `AllowedPeers` получателя — это видимое решение в коде, а не умолчание.
- Альтернатива (b) — авторизация в Envoy RBAC по маршрутам — не выбрана как основная: права решает сервис-владелец (CLAUDE.md), RBAC в mesh можно добавить позже как дополнительную защиту.
