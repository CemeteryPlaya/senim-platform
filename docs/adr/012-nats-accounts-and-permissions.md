# ADR-012: Учётные записи и права NATS

Статус: принято (финальная волна исправлений плана 1, 08.11.2026; решение контроллера по замечанию I2 финального ревью).

## Контекст

В плане 1 NATS работал без аутентификации, прав и TLS (`nats -js`, порт 4222 на 127.0.0.1 хоста и в сети compose). Конфиг сервиса знал только `NATS_URL`. Гарантии outbox/inbox защищали от повторов, но не от подделки: любой контейнер или процесс хоста мог положить корректный конверт в `senim.deal.*`, и получатель обработал бы его ровно один раз. По спеке (§4.3) `marketplace` открывает контакты по `OfferConcluded` от `deal` — подделанное событие стало бы путём к раскрытию контактов. Конфиг подключения копируют все сервисы планов 2–6, а первые получатели событий появляются в плане 2.

## Решение

1. **Учётная запись на каждый Go-сервис** (`user` = имя сервиса, пароль). Права:
   - публикация — только `senim.<сервис>.>` и API JetStream своего потока: `$JS.API.STREAM.CREATE|UPDATE|INFO.SENIM_<СЕРВИС>` (это всё, что делают `outbox.EnsureStream` и релей);
   - подписка — только свой префикс ответов `_INBOX_<сервис>.>` (`natsx.InboxPrefix`; клиент ставит `nats.CustomInboxPrefix`), то есть подтверждения своих публикаций и ответы API. Общий `_INBOX.>` не выдаётся: иначе сервис читал бы чужие ответы;
   - всё остальное запрещено сервером (`Permissions Violation`), в том числе чужие субъекты, чужие потоки и широкие подписки.
   Получатели событий (план 2) добавляют права своего консьюмера на поток источника — `$JS.API.CONSUMER.CREATE|INFO|MSG.NEXT.SENIM_<ИСТОЧНИК>.<получатель>…` и `$JS.ACK.SENIM_<ИСТОЧНИК>.<получатель>.>` — в `tools/natsconf.Permissions` вместе с тестом на живом NATS. Сейчас получателей нет, и в конфиге этих прав нет.
2. **TLS обязателен**, сервер требует клиентский сертификат внутреннего CA (`tls.verify`): серверный сертификат `nats` выпускает devcerts, клиент — тот же сертификат сервиса, что для gRPC (`TLS_*`), TLS 1.3. Пароль и сертификат вместе: утечка одного не даёт входа.
3. **Конфиг сервера генерируется** так же, как роли БД: `tools/natsconf` читает dev-пароли `<SVC>_NATS_PASSWORD` из `deploy/compose/dev.vars` и пишет `deploy/compose/nats/nats.conf` (`npm run v2:config`); тест сверяет закоммиченный файл с генератором байт в байт. Список сервисов — `tools/services`. Мониторинг NATS слушает только 127.0.0.1 внутри контейнера (healthcheck).
4. **Конфиг сервиса** (`pkg/natsx`): `NATS_URL`, `NATS_USER`, `NATS_PASSWORD` (секрет). Вне dev: каждый адрес — `tls://`, учётная запись обязательна, пароль — base64 ≥ 32 байт; в dev допустимы `nats://` и вход без учётной записи (тесты на голом NATS). `natsx.Connect` — имя соединения, бесконечные переподключения, свой префикс ответов, TLS, запись в лог потери/восстановления соединения и асинхронных ошибок сервера (нарушения прав).
5. **Источник события проверяет получатель**: `inbox.Handle` делает Term без обработчика, если `envelope.source` не совпадает с источником субъекта `senim.<source>.…`. За субъект ручаются права NATS (п. 1), за конверт — только публикатор, так что подделать источник нельзя ни через субъект, ни через конверт.

## Проверка

- `pkg/natsx` на NATS с закоммиченным `nats.conf`: identity создаёт и обновляет свой поток и публикует в `senim.identity.*`; поток `deal`, публикация в `senim.deal.*`, подписки на `senim.>` и `_INBOX_deal.>` отвергнуты сервером; вход без учётной записи, с чужим паролем, неизвестным пользователем, без клиентского сертификата и без TLS — отказ; правила `Load` для dev и prod/staging.
- `tools/natsconf`: закоммиченный конфиг совпадает с генератором; права — только свои.
- `services/identity`: сервис поднимается на NATS с TLS и учётной записью.
- `pkg/inbox`: источник конверта не совпал с субъектом — Term, 0 записей inbox.
- Живой стенд (`test/smoke`): web без учётной записи и соединение без TLS отвергнуты; identity с учётной записью и сертификатом подключается, публикация в `senim.deal.*` — `Permissions Violation`.

## Последствия

- Плюс: подделать событие чужого сервиса нельзя ни из контейнера стенда, ни с хоста; шаблон подключения для семи сервисов плана 2 готов.
- Минус: пароли в `nats.conf` стенда открытым текстом (NATS предупреждает: «Plaintext passwords detected») — это dev-заглушки, как пароли ролей БД; в prod пароли (или nkeys/JWT-аккаунты) выдаёт менеджер секретов (план 7), конфиг сервера — не из репозитория.
- Минус: сервис сам создаёт свой поток, и право `STREAM.CREATE|UPDATE` не ограничивает субъекты внутри конфига потока: скомпрометированный сервис мог бы занять поток с чужими субъектами раньше владельца (NATS не даёт двум потокам пересекаться по субъектам). В prod потоки создаёт провиженинг (IaC/оператор), а сервисам остаётся только `STREAM.INFO` — решить в плане 7.
- Минус: нарушение прав при публикации JetStream видно не сразу — подтверждение не приходит, и релей ждёт тайм-аут публикации (5 с), а запись получает учёт неудачной попытки; причина — в логе (`nats: ошибка сервера … Permissions Violation`).
